# openFDA MCP Server

## Overview

Wraps the [openFDA API](https://open.fda.gov/apis/) -- an Elasticsearch-backed public API serving FDA data across drugs, food, devices, and other regulated products. Covers adverse event reports (20M+ drug, 24M+ device, plus food and cosmetic), enforcement/recall actions (140K+ across all categories), drug labels, the NDC directory and the NSDE package file, drug approvals (Drugs@FDA), the Orange Book, Complete Response Letters, drug shortages, device 510(k) clearances (174K+), PMA approvals, device classifications, and more — 24 endpoints in all.

All endpoints share a uniform query interface (`search`, `count`, `sort`, `limit`, `skip`) with Elasticsearch syntax. Optional free API key increases daily limit from 1,000 to 120,000 requests.

**Dependencies**: None beyond HTTP. No official SDK -- the API is straightforward REST/JSON.

## Tools

**Shared `search` / `sort` contract.** Wherever a tool below takes a caller-supplied `search`, every double quote, parenthesis, and range bracket it opens must close, and it must not end on a backslash — each raises `malformed_search` locally, before the request, as does a character openFDA refuses anywhere in a query (`!`, `#`, `$`, `;`, `?`, `^`, `|`, `~`, the backtick, and any character outside printable ASCII that is not whitespace): the message names the character (`U+XXXX` when it is not ASCII) and its 1-based position, and a refused character is checked ahead of the delimiters. Whitespace other than the space (a tab, a line break, a no-break space) reads as a space, and an unquoted term of letters and digits joined by hyphens (`D-0123-2024`, `0003-0894`) is sent as a quoted phrase, which shows in the echoed query. Wherever it takes a `sort`, the value is one or more comma-separated field paths (multi-field sort is supported, and spaces around a segment are fine), each optionally suffixed with `:asc` or `:desc` — in any letter case, with `ascending` and `descending` also accepted, each sent upstream as lowercase `asc` or `desc`; a field path holds only letters, digits, underscores, and dots, and any other direction is rejected. A search sent without a `sort` returns records in openFDA's index order, not relevance; the default a call naming neither `search` nor `sort` sends is the date field listed under the shared browse contract. A `+` between clauses (openFDA's URL-form spelling of a space) reads as a space; inside a quoted phrase it is a literal plus. See [Query hygiene](#implementation-notes). Where a tool composes a query from a caller-supplied *term* instead — `openfda_drug_profile` — the term is read once, each run of whitespace and refused characters becoming one space, and escaped for its phrase context rather than rejected. Grammar, rationale, and boundaries: [Query hygiene](#implementation-notes).

**Shared size contract.** `limit` is the page size, with a per-endpoint default and cap (`PAGE_SIZES` in `schema-utils.ts`); a larger value is clamped to the cap with a notice, or rejected when `OPENFDA_CLAMP_LIMITS=false`. A page is never cut to a byte budget. A page holding a record that serializes above 24,000 bytes on its own reports `page_bytes` and `page_largest_fields`; `openfda_get_drug_label` overflows to a section outline at the same figure, because its payload is one document rather than many rows. Both are described under [Response size](#response-size), along with the tools the cap does not reach. A page read without `fields` leaves the heaviest named paths out of each record on three endpoints (`drug/event`, `device/enforcement`, `device/recall`), names them in `omitted_fields`, and returns them through `include` ([Field selection](#field-selection-fields)).

**Shared browse contract.** A call to `openfda_search_adverse_events`, `openfda_search_recalls`, `openfda_search_drug_approvals`, `openfda_search_device_clearances`, `openfda_search_animal_events`, `openfda_search_drug_shortages`, or `openfda_search_tobacco_reports` that names neither `search` nor `sort` is a browse and sends its date field descending, so it leads with the newest records (`sortOrNewest`, `src/mcp-server/tools/default-sort.ts`). An explicit `sort` is sent as given; a `search` with no `sort` sends none, which keeps the mirror's exact-key routing and returns records in openFDA's index order, not ranked by relevance (an unsorted request pages by document id alone; `sort` it when order matters). `openfda_lookup_ndc` and `openfda_get_drug_label` have no default sort, nor has the `classification` pathway of `openfda_search_device_clearances`, whose records carry no date.

**Shared paging contract.** The nine paging tools — the eight multi-row search tools and `openfda_get_drug_label` — take `skip` and `cursor` and return `next_cursor` (`src/mcp-server/tools/pagination-cursor.ts`). `skip` pages as far as openFDA's 25,000-record ceiling (`OPENFDA_MAX_SKIP`); a page read at `skip` 0 or by cursor returns `next_cursor` only when openFDA linked a next page the walk can follow and matched records remain, and passing it back as `cursor`, with no `skip`, reads the next page, and the walk is not bound by the ceiling. The endpoint, `search`, and `sort` may not change between pages; every other input (`limit`, `fields`, `include`, `sections`) may. `meta.skip` on a cursor page is the walk position, the records returned before it; `meta.total` is the match total. The page holding the last matched record carries a notice that the walk is complete and no `next_cursor`. A sorted walk that reaches the records lacking a sort field, which openFDA sorts last, is linked with that sort key's missing-value marker, and following such a link fails (a date sort) or loops (a keyword sort: ascending restarts the walk at its first record, descending repeats one page forever): that page carries no `next_cursor`, and a notice names the routes on, `skip=<position>` while within 25,000, an `_exists_:` clause per sort field in the `search`, or another sort. A link that repeats the page it was read from gets no `next_cursor` either, and its notice names `skip` with the same search (and sort), or narrowing the search. A cursor is read inline: with `skip` above 0, `stage: true`, or `canvas_id` it is refused as `invalid_cursor`, and a staged call never returns `next_cursor`. A token that does not decode, or that was issued for another endpoint, `search`, or `sort`, fails `invalid_cursor` before any request. A tool that picks its endpoint from another input (`category`, `endpoint`, `dataset`, `pathway`) binds the token to the endpoint the call resolves to.

**Decision — a cursor wraps openFDA's own `search_after` value and is bound to its query, with no key.** openFDA refuses a `skip` above 25,000, but it links a `search_after` continuation from any page read at `skip` 0 or by `search_after`, and a continuation is not bound by the ceiling. The token is base64url JSON of three fields: the walk position `p`, openFDA's `search_after` value `a` verbatim, and `q`, the first 11 base64url characters of the SHA-256 of `[endpoint, search, sort]` as the call sends them, after the schema's normalization and any default sort. openFDA answers a `search_after` taken from another endpoint, another search, or the opposite sort direction with HTTP 200 and silently repositioned records, so a token presented with a different query must fail before the request; the hash exists for that and nothing else. It carries no HMAC: a caller who edits a token can only reposition its own query, which `skip` already allows. The server never fetches the `Link` URL the value came from. The service keeps only the `search_after` parameter of the `rel="next"` link and rebuilds every request from the caller's validated inputs, sending `skip=0` beside it (openFDA answers `search_after` with a `skip` above 0 as a 400), so a token positions a walk and cannot choose a request. The service reports the walk position as `meta.skip`, since openFDA reports `skip: 0` on every `search_after` page, and the next position advances by the records the page holds, never by the requested `limit`, so a clamped or short page skips nothing.

**Decision — a link the walk cannot follow is withheld, not handed out.** A token for a link carrying a sort key's missing-value marker (`±9223372036854776000` on a date sort, the empty value on a keyword sort) fails the caller's next request or loops, serving records already read, so the service reads the marker (`continuationOf`, `openfda-service.ts`) and reports the link as blocked instead of continuable. No `next_cursor` plus a notice with the way on costs the caller no request; a token that fails or repeats costs one and says nothing about why.

**Decision — a bare browse sends a newest-first sort.** openFDA answers a request with no `sort` in index order, so a call with neither `search` nor `sort` led with records decades old (device adverse events from 1992 as of 2026-11-10). With both omitted, each search tool sends its date field descending on the inline query and on the staged probe, window, and drain: adverse events `receivedate:desc` (drug), `date_created:desc` (food), `date_received:desc` (device), `initial_received_date:desc` (cosmetic); recalls `report_date:desc` (`event_date_initiated:desc` on `endpoint: recall`); device clearances `decision_date:desc` (510(k) and PMA); animal events `original_receive_date:desc`; drug shortages `update_date:desc`; tobacco `date_submitted:desc`; Drugs@FDA `submissions.submission_status_date:desc`, which orders applications by their latest submission status date, supplements included, not by approval date; the Orange Book `approval_date:desc`; Complete Response Letters `letter_date:desc`. Cosmetic reports sort on `initial_received_date`, the date FDA first received a report, as drug reports sort on `receivedate`: `latest_received_date` leads with follow-ups to years-old reports. Shortages sort on `update_date`, which is on or after `initial_posting_date` on every sampled record, so a new posting leads too. `device/classification` has no browse sort: its records carry no date, `decision_date:desc` answers HTTP 500 there, `product_code:asc` answers 400, and only `device_name.exact` and `regulation_number.exact` sort. No tie-breaker is added: many records share a date, but openFDA pages ties in a stable order on the date alone (a `skip=5` page equals items 6–10 of a 10-row page, a repeat returns the same ids, and 3-page walks and drains of the other tools showed no duplicate or missing record, 2026-11-10; shortages tie on `update_date` and page stably the same way). The sorted bare request is also faster upstream (drug adverse events 1.7 s against 3.4 s, device 1.2 s against 3.3 s).

**Decision — each rule a description states has one source, and a description repeated across tools stays short (cyanheads/openfda-mcp-server#109).** A client loads the whole tool catalog before its first call, so every description byte is paid on every session, and a rule restated on each of ten tools is paid ten times and drifts. Each rule a description states is written once, in a shared builder: `sortDescription`, `fieldsDescription`, and `SKIP_DESCRIPTION` in `schema-utils.ts`, `SEARCH_SYNTAX_NOTE` in `search-expression.ts`, `stageInput` and `canvasIdInput` in `src/services/openfda/canvas-spill.ts`. A description repeated verbatim on two or more tools stays at or under 300 bytes, and a shared clause appended to per-tool text at or under 120. Guidance that prevents a silent wrong answer stays on the property, shortened (a search sent without a `sort` returns openFDA's index order, not relevance; a `+` inside a quoted phrase is a literal plus). Text restating a rule the server enforces locally is dropped, because the enforcement already tells the caller: an immediate rejection (`malformed_search`), a schema `pattern` (the `sort` grammar, the `fields` path), or automatic normalization (whitespace and URL-form `+` separators, shortage dates). `tests/mcp-server/tools/definitions/wire-contract.test.ts` holds the repetition bound, the clause bound, and a ceiling on the bytes of server-written description text across the tool definitions.

### `openfda_drug_profile`

Resolve one drug name to its FDA identity, then fan out in parallel to the bounded per-drug endpoints and merge into a single consolidated profile. Replaces chaining `openfda_get_drug_label`, `openfda_search_adverse_events`, `openfda_search_recalls`, `openfda_search_drug_approvals`, and `openfda_search_drug_shortages`, and reconciles the identifier drift between endpoints that makes that chaining error-prone.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `drug` | string | Yes | Drug name — brand or generic (e.g. `metformin`, `Humira`). Resolved once to an FDA identity, each run of whitespace and characters openFDA cannot search (such as `;` or `®`) read as one space. The Drugs@FDA approval is ranked over this name's matches; `meta.fanOutKey` reports the name the recall and shortage sub-queries searched. |

`drug_name` and `name` are accepted as aliases of `drug` (`inputAliases`), rewritten before validation and never advertised — `drug` stays the only parameter in `inputSchema`. An alias sent alongside `drug` is rejected as an unknown key.

**Behavior.** One profile deadline, 50 s from the start, bounds every request of every round (`deadlineAtMs` on `OpenFdaService.query`). A request it cuts lands in `degraded` with reason `timeout`, never failing the call.

The typed name is read once (`searchableName`): accents are folded first (canonical decomposition, combining marks dropped, so `Néoral` reads `Neoral`, as openFDA stores it), then each run of whitespace and of characters openFDA refuses in a query (`;`, `®`, a line break) becomes one space and the ends are trimmed. A character with no canonical decomposition (`™`, `®`, `ø`, a CJK character) still becomes a space and breaks the word. Every phrase the tool builds, the Drugs@FDA ranking, and the fan-out key use those words, and a resolved generic or brand name taken from a record passes through the same reading. A name with no ASCII letter or digit after that reading, one of only combining marks included, raises `blank_drug_name`.

Round 1 runs `(openfda.generic_name:"<term>" OR openfda.brand_name:"<term>") AND openfda.is_original_packager:true` on `drug/label` (best single-ingredient match; combination products are de-prioritized so a single-drug query doesn't resolve to a combo). Beside it runs the Drugs@FDA selection `((openfda.generic_name:"<term>" OR products.active_ingredients.name:"<term>") AND (application_number:NDA* OR application_number:BLA*)) OR (products.brand_name:"<term>" AND NOT products.active_ingredients.name:"<term>")` at limit 100. Only when no original packager's label matches does round 2 run the unrestricted label search beside the `drug/ndc` fallback (a label wins).

`pickApplication` ranks the selection on each application's own `products[]`, never its `openfda` block, tier by tier:

- a brand name equal to the input that is not made of its ingredient names;
- one ingredient (several when the key names a combination);
- ingredients without a biologic `-xxxx` suffix, led by the key's words;
- `reference_drug: "Yes"`;
- NDA/BLA over ANDA;
- Prescription or Over-the-counter, over Discontinued, over tentative or none;
- the lowest application number.

An application ranks as its best product.

Recalls and shortage key on `meta.fanOutKey`, derived from the label the name matched: the supplied term when its words appear consecutively, in order and case-insensitively, in the resolved generic name (the caller typed an ingredient: `adalimumab` against a label whose generic is `ADALIMUMAB-AACF`), otherwise the resolved generic name, then a brand name, then the term — so brand input (`Lipitor`, `Glucophage`) still keys on the generic, never the brand. The rule applies to an identity resolved through `drug/ndc` too. Round 3 fans out: the three `drug/event` queries; recalls (`openfda.generic_name:"<key>" OR product_description:"<key>"`, newest 5 by `report_date`, plus the match total in `recalls_total`); shortage (`generic_name:"<key>"`, newest 100 by `update_date`). It adds one of:

- the picked application's original-packager label (`openfda.application_number:"<pick>" AND openfda.is_original_packager:true`), which replaces identity and label when the label in hand is not it;
- when the selection matched nothing, `openfda.generic_name:"<key>" OR products.active_ingredients.name:"<key>"` at limit 100, ranked the same way.

Shortage shows one record — for brand input the newest naming the brand by product or presentation, else the newest — with its product, company, presentation, the match total, and per-status counts; `namesInput: false` marks another product's record. A selection or shortage total above 100 raises a notice. A failed label lookup degrades `label` only when no label is left in hand; otherwise a notice names it and whose label is shown.

The free-text adverse-event field (`drug/event` `patient.drug.medicinalproduct`) queries by the typed name as normalized, for better recall. Each section is best-effort: a failed or empty sub-query yields `null` (or `[]` for recalls) rather than failing the whole call. An empty `recalls` or a null `approval` names the fields it searched rather than claiming no record exists; a failed recall search reports `recalls_total: null` (listed in `degraded`), never 0. The adverse-event section takes three `drug/event` sub-queries for the same search — a `limit=0` request whose `meta.results.total` is the section's `total`, the `serious` tally, and the top-reaction tally — and is `null`, with one `adverse_events` entry in `degraded`, when any of the three fails.

A profile costs 7 upstream requests when the original packager's label already belongs to the picked application, 8 when the by-application lookup or the approval fallback runs, and 10 when no original packager's label matches — at most three rounds.

**Returns:** `meta` (echoed `drug`, `resolvedVia`, `fanOutKey`) + `identity` (`brand_names`, `generic_name`, `manufacturer`, `product_ndc`, `application_number`, `is_original_packager`, `rxcui`, `spl_set_id`) + `label` (`indications`, `warnings`, `dosage`) + `adverse_events` (`total`, `seriousCount`, `topReactions[]`) + `recalls[]` (`recall_number`, `status`, `classification`, `reason`, `recalling_firm`, `date`) + `recalls_total` (number of `drug/enforcement` reports the recall search matched — `recalls[]` is the newest 5 of them; `null` when that sub-query failed) + `approval` (`applicationNumber`, `sponsor`, `marketingStatus`, `approvalDate`, `reviewPriority`, `submissionClass`, `brandNames`, `candidates`) + `shortage` (`status`, `availability`, `product`, `company`, `presentation`, `namesInput`, `total`, `statusCounts[]`). Sections are `null` when unavailable. When `identity.application_number` and `approval.applicationNumber` differ, `content[]` says identity and label come from a different application. `adverse_events.total` counts every report the search matches, those with no seriousness recorded included, so it equals `openfda_search_adverse_events` `meta.total` for `patient.drug.medicinalproduct:"<drug>"`; `seriousCount` is the `serious=1` bucket. `recalls[].recall_number` is `null` on a report whose `recall_number` is empty; a recall's lots (`code_info`) and distribution pattern come from `openfda_search_recalls` with `category: drug` and `search: recall_number:"<recall_number>"`. `approval.approvalDate`, `reviewPriority`, and `submissionClass` all come from one submission of the picked application: among its `submissions[]` typed `ORIG` with status `AP`, the earliest `submission_status_date`, ties to the lowest `submission_number`, with array order ignored. `approvalDate` is that date as stored (`YYYYMMDD`), `reviewPriority` its `review_priority` verbatim, and `submissionClass` its `submission_class_code_description`, else its `submission_class_code`. All three are `null` when no submission qualifies — a tentative approval only, a record that starts at a supplement — and a supplement's date is never read.

**Decision — the adverse-event total is a `limit=0` search, not a sum of `serious` buckets.** A count response carries no total, and the buckets cover only reports that record a `serious` value — metformin's sum fell 106 short of its match total, aspirin's 257. One extra request per profile buys the exact figure; a `seriousnessUnknown` field was not added, since `total − seriousCount` already includes those reports and the `total` description says so.

**Decision — a typed ingredient keys the structured sub-queries.** The key was the one resolved label's `openfda.generic_name`, and the best-match tie-break can pick a single product's string: `adalimumab` keyed on `ADALIMUMAB-AACF` (1 Drugs@FDA application where `adalimumab` matches 11 — the count the approval fallback sees — and no shortage where it matches 6), `metformin` on `METFORMIN ER 500 MG` (1–2 recalls against 33). The typed term is used only when its words are whole words of the resolved generic, so brand input keeps keying on the generic. The match is word-for-word (letter/digit runs, case-insensitive), the split openFDA's analyzer makes of a quoted phrase, and runs as Knuth–Morris–Pratt so it stays linear on caller text. Rejected: the most common `openfda.generic_name.exact` across label matches (fragments biosimilars and costs a request) and `openfda.substance_name` (`ATORVASTATIN CALCIUM TRIHYDRATE` does not phrase-match `ATORVASTATIN CALCIUM`). (Figures measured 2026-10-26.)

**Decision — recalls and approval also search each record's own field, and recalls report a total.** openFDA fills `openfda.*` only where it harmonized the record: 3,097 of 18,043 enforcement reports and 11,789 of 29,416 Drugs@FDA applications. `insulin glargine` matched no recall on `openfda.generic_name` and 3 on `product_description`; `troglitazone`'s two NDAs carry no `openfda` block. Widening alone would still show 5 rows with no count, so `recalls_total` reports the match total (`metformin`: 5 of 91). The composed `OR` relies on the service's parenthesized `search`. No precision filter: in 111 sampled description-only matches one was unrelated. (Figures measured 2026-10-26.)

**Decision — each section is chosen by a rule and names its product.** The first record an arbitrary window returned stood in for the drug: a repackager's NDC for metformin (A-S Medication Solutions, 50090-7011), a biosimilar's label for adalimumab, a generic's application for Lipitor, another product's presentation for Humira's shortage. `is_original_packager` is true on 65,436 of 87,575 labels with an `openfda` block and never false, and no A-S Medication Solutions, Bryant Ranch Prepack, or RemedyRepack label carries it, so the label search asks for it first. Drugs@FDA's `openfda` block drops a biologic's suffix (`TRASTUZUMAB` for `TRASTUZUMAB-PKRB`), so ranking reads `products[]`. `reference_drug` marks 3,854 of 5,910 NDAs and no BLA, so it ranks after the ingredient tiers. The by-application lookup shares round 3 with the fan-out rather than adding a round, so the fan-out key comes from the label the name matched. (Figures measured 2026-11-10.)

**Decision — the approval's date, priority, and class come from the one submission that made the original approval.** A `submissions[]` array is not in date order and carries supplements, each with its own status date, so reading its first entry or its latest date states a supplement's facts as the approval's. The earliest `ORIG` submission with status `AP` is the approval, and its three facts are read together so they describe one submission; a tentative approval, or a record that starts at a supplement, has no such submission and reports `null` rather than a nearby date. Each recall carries its `recall_number` so the one record can be re-read with its lots and distribution through `openfda_search_recalls`; the profile itself stays at five rows and never carries those lists.

### `openfda_search_adverse_events`

Search adverse event reports across drugs, food, devices, and cosmetics. Use to investigate safety signals, find reports for a specific product, or explore reactions by demographics. The primary research tool for safety data.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `category` | `"drug"` \| `"food"` \| `"device"` \| `"cosmetic"` | Yes | Product category, read from `<category>/event`. Each has different field schemas -- drug reports include patient demographics and suspect drugs, device reports include device details and event type, food reports include industry and outcomes, cosmetic reports include the products with their role, the reactions, and the outcomes. |
| `search` | string | No | Elasticsearch query string. Clauses joined by `AND`, `OR`, `NOT`, or a space (implicit OR); the URL-form `+AND+` / `+OR+` of openFDA's docs also works. Examples: `patient.drug.medicinalproduct:"aspirin"`, `patient.reaction.reactionmeddrapt:"nausea" AND serious:"1"`. Omit both `search` and `sort` to browse the newest reports first. |
| `sort` | string | No | Sort field and direction. Sortable date fields are category-specific: drug → `receivedate` (or `receiptdate`), food → `date_created` (or `date_started`), device → `date_received` (or `date_of_event`), cosmetic → `initial_received_date` (or `latest_received_date`). A field from another category (e.g. `receivedate` on food or device) is refused as `not_sortable`. With `search` also omitted the default is newest first (`receivedate:desc`, `date_created:desc`, `date_received:desc`, `initial_received_date:desc`); a `search` with no `sort` sends none. |
| `limit` | number | No | Records per page. Default and cap by `category`: drug 5 (cap 25), food 25 (cap 1000), device 10 (cap 175), cosmetic 25 (cap 1000). A larger value is clamped to the cap with a notice, or rejected with `OPENFDA_CLAMP_LIMITS=false`. See [Response size](#response-size). |
| `skip` | number | No | Pagination offset. Above 25000 the handler raises `pagination_limit_reached`; `cursor` reads past it. |
| `cursor` | string | No | The `next_cursor` of the previous page, sent with the same `search` and `sort` and no `skip` (other inputs may change); bound to the category's endpoint, and refused beside `stage` or `canvas_id`. See the [shared paging contract](#tools). |
| `fields` | string[] | No | Dotted record paths to keep on each record (e.g. `patient.drug.medicinalproduct`), plus its identity key; a path through an array applies to every element, and the oversized-record disclosure measures the projected records. A path no record on the page carries is named on the notice. Without `fields`, a drug page leaves `patient.drug.openfda` out (`include`). See [Field selection](#field-selection-fields). |
| `include` | string[] | No | Paths a default page leaves out, to return: `patient.drug.openfda` on drug, or a path beneath it for that field alone (`patient.drug.openfda.brand_name`). With `fields`, an entry naming a left-out path joins the projection; an entry naming none changes nothing. |

**Returns:** `meta` (total count, skip, limit) + array of adverse event records. Drug records include `safetyreportid`, `patient` (age, sex, reactions[], drugs[]), `serious` flag, `receivedate`. Device records include `report_number`, `device[]` (brand, generic name, manufacturer), `event_type`. Food records include `reactions`, `outcomes`, `products`. Cosmetic records include `report_number`, `initial_received_date`, `latest_received_date`, `patient`, `reactions`, `outcomes`, and `products[]` (`product_name`, `role`); `content[]` renders each under a `### Report <report_number>` heading with both receipt dates, then one list item per product with its role, then every other field. A page read at `skip` 0 or by cursor carries `next_cursor` while records remain and openFDA's next link can be followed. A default drug page names `patient.drug.openfda` and its bytes on that page in `omitted_fields` and in a notice, and a `search` clause on that path or beneath it returns it. In `content[]`, each drug report lists its reactions one item each, term with outcome (`Death — fatal (5)`); a MedDRA version every reaction shares heads the list once (`**Reactions (MedDRA 29.0):**`), and differing versions render on each item. Onset age renders with its unit (`3 month (802)`). Coded fields render their meaning beside the raw code from the shared tables in `src/mcp-server/tools/drug-event-codes.ts` (labels from FDA's drug/event field reference): `drugadministrationroute` (`via oral (048)`), `reactionoutcome`, `patientagegroup` (`elderly (6)`), `patientonsetageunit`, the per-drug `actiondrug`, `drugadditional`, `drugrecurreadministration`, `drugtreatmentdurationunit`, `drugintervaldosagedefinition`, `drugstructuredosageunit`, `drugcumulativedosageunit`, and the report-level `reporttype`, `fulfillexpeditecriteria`, `primarysource.qualification`, `sender.sendertype`, `receiver.receivertype`. A code the tables lack renders unchanged: a name such as `ORAL`, codes FDA's reference leaves undefined (`drugadditional` 4, `fulfillexpeditecriteria` 3–5, `sendertype` 1, 4, 6), `drugintervaldosagedefinition` 807 (FDA labels 807 and 811 both "Trimester"), and dose-unit codes 005 and above. Every list in a drug or food report ends with a blank line, so the fields after it render outside its last item. `structuredContent`, `fields`-projected records, `openfda_count_values` terms, and staged canvas rows keep the raw codes.

**Decision — the code tables live in one module the field catalog reads from.** The catalog notes for the coded `drug/event` fields interpolate labels from `drug-event-codes.ts` instead of restating them, so the `openfda_describe_fields` note and the search tool's render cannot drift apart. Labels are FDA's field-reference wording, lower-cased, with its two misspellings corrected (`049` oropharyngeal, `057` subconjunctival).

**Cross-entry notice.** On all four categories, a matched search whose AND-ed clauses fall under one array of objects carries a notice naming the array, its fields, and the SQL for one entry ([Clauses on one array](#implementation-notes)). The arrays are `patient.drug` and `patient.reaction` on drug, `device`, `patient`, and `mdr_text` on device, and `products` on food and cosmetic; a drug array sits inside the staged table's `patient` column.

### `openfda_count_values`

Aggregate and tally unique values for any field across any openFDA endpoint. Use for trend analysis, frequency distributions, and "top N" questions. Returns `[{term, count}]` pairs instead of individual records.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `endpoint` | string | Yes | Full endpoint path, one of the 24 the field catalog lists: `drug/event`, `drug/label`, `drug/enforcement`, `drug/ndc`, `drug/drugsfda`, `drug/orangebook`, `drug/shortages`, `food/event`, `food/enforcement`, `cosmetic/event`, `device/event`, `device/510k`, `device/pma`, `device/recall`, `device/enforcement`, `device/classification`, `device/registrationlisting`, `device/udi`, `device/covid19serology`, `animalandveterinary/event`, `tobacco/problem`, `other/substance`, `other/nsde`, `transparency/crl`. New endpoints are rare -- check [open.fda.gov/apis](https://open.fda.gov/apis/) if a category seems missing. |
| `count` | string | Yes | Field to count — the `countAs` expression `openfda_describe_fields` lists for the field. Outside the catalog: append `.exact` to an analyzed text field (openFDA refuses to aggregate it bare), count a keyword field bare. Examples: `patient.reaction.reactionmeddrapt.exact`, `classification.exact`, `product_ndc`. |
| `search` | string | No | Filter query to scope the count. Example: `patient.drug.medicinalproduct:"metformin"` to count reactions only for metformin. |
| `limit` | number | No | Number of top terms to return. Default 100, cap 1000 (openFDA answers a count `limit` above 1000 with HTTP 400); a larger value returns 1000 terms with a notice naming the requested value, or fails argument validation with `OPENFDA_CLAMP_LIMITS=false`. |

A date field (`receivedate`, `report_date`, `decision_date`) is counted bare and yields one term per distinct `YYYYMMDD` date.

On `drug/shortages`, a calendar date written `YYYYMMDD`, `M/D/YYYY`, or `YYYY-M-D` on `initial_posting_date`, `update_date`, `discontinued_date`, or `change_date` is rewritten to `YYYY-MM-DD` before the request, as `openfda_search_drug_shortages` rewrites it ([Dates on `drug/shortages`](#implementation-notes)). The tool echoes no query, so the rewritten form shows only where a notice quotes the `search`. A `field:(…)` group on one of those fields is sent as written, so a count that matched nothing under one says to write each date in it `YYYY-MM-DD`.

A count whose `search` has AND-ed clauses under one array of objects carries a notice, since openFDA tests each clause against the whole record and a tally over the records that match cannot say whether one entry met them together ([Clauses on one array](#implementation-notes)). The notice names the endpoint's search tool with the input that selects the endpoint (`category: "drug"`, `dataset: "orangebook"`) and `stage: true`, and the `WHERE` condition that selects one entry in the staged table; it is silent on an empty tally. It covers the eight endpoints that have both a search tool and a surveyed array of objects: `drug/drugsfda`, `drug/orangebook`, `drug/event`, `device/event`, `food/event`, `cosmetic/event`, `animalandveterinary/event`, and `drug/ndc`.

**Returns:** Array of `{term, count}` objects sorted by count descending. Example: `[{"term": "NAUSEA", "count": 752664}, {"term": "FATIGUE", "count": 742326}]`. A date field comes back from openFDA as `{time, count}` buckets; each bucket's date becomes its `term` (`"20240103"`), keyed on the row shape rather than the field catalog, since openFDA also buckets date fields the catalog does not type. A count row with no value or no numeric count is left out, and the `notice` says how many.

**Decision — truncation comes from a look-ahead term.** Count responses carry no distinct-term total in `meta`, so the handler requests `min(limit + 1, 1000)` terms and returns the first `limit`; `limit` is the applied value, after any clamp. `truncated` (with `shown`, `cap`, `truncationCeiling`) is set only when the extra term arrived — it costs no request, and ranking is stable between `limit` and `limit + 1`. Treating exactly `limit` rows as truncated reported a complete list (a binary field at `limit: 2`) as capped. At `limit: 1000` no look-ahead fits, so a full 1000-term list omits `truncated` and the `notice` says openFDA cannot show whether more distinct values exist; narrowing with `search` is the way past it.

**Decision — date buckets are ranked in the handler, and their truncation is exact.** openFDA ignores `limit` on a date count and sends every bucket in ascending date order, so slicing the first `limit` rows returned the oldest dates labeled as the top N by count. The handler ranks every bucket by count descending, ties by date ascending, then applies `limit`, keeping the count-descending contract and making `truncationCeiling` meaningful. Because every bucket is in hand, `truncated` is set exactly when more dates exist than `limit`, its notice names how many distinct dates were counted, and the 1000-term "cannot show whether more distinct values exist" notice never applies to a date count. A caller wanting the full series scopes `search` to at most `limit` dates; `YYYYMMDD` terms sort chronologically. Rejected: keeping date order — it would need a second ordering contract for one field type.

**Count-only endpoints.** Four endpoints are reachable via `openfda_count_values` but have no dedicated search tool; every other endpoint it counts is a search tool's, selected by `category`, `endpoint`, `dataset`, or `pathway` where one tool serves several:

| Endpoint | Reason no search tool |
|---|---|
| `device/registrationlisting` | Registration/listing data (320K records). Primarily useful for facility lookups -- low priority vs. the higher-signal 510(k)/PMA/recall tools. |
| `device/udi` | Large dataset (4.9M records) but very granular device identifier data. UDI lookups are niche -- most device research uses 510(k) or classification. |
| `device/covid19serology` | Narrow domain. Count-only unless serology test data becomes a priority. |
| `other/substance` | Substance/ingredient reference data. Count covers "what substances exist" queries. |

These endpoints all support the standard `search`/`count`/`limit`/`skip` parameters. If a use case emerges requiring individual record access, promote to a full search tool.

### `openfda_get_drug_label`

Look up FDA drug labeling (package inserts / SPL documents). Use to check indications, warnings, dosage, contraindications, active ingredients, or any structured label section for a drug.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `search` | string | Yes | Query targeting label fields. Common patterns: `openfda.brand_name:"aspirin"`, `openfda.generic_name:"metformin"`, `openfda.manufacturer_name:"pfizer"`, `set_id:"uuid"`. Combine with `AND` for specificity. `set_id` returns the label's current revision only; openFDA does not serve earlier ones. |
| `sort` | string | No | Sort field and direction. Example: `effective_time:desc` for most recent labels. No default: a search without `sort` returns openFDA's index order. |
| `limit` | number | No | Labels per page. Default 5, cap 1000; a larger value returns 1000 records with a notice naming the requested value, the cap, and the next `skip` (`OPENFDA_CLAMP_LIMITS=false` rejects it instead). Labels are large -- keep limit low unless browsing; a section's retrieval cost is summed across the page, so it scales with this limit. |
| `skip` | number | No | Pagination offset. Above 25000 the handler raises `pagination_limit_reached`; `cursor` reads past it. |
| `cursor` | string | No | The `next_cursor` of the previous page, sent with the same `search` and `sort` and no `skip`. See the [shared paging contract](#tools). |
| `sections` | string[] | No | Top-level label sections to return, e.g. `["boxed_warning","indications_and_usage"]`. Omit for the whole label; an empty list is treated as omitted. Returned whole even when the projection exceeds the 24,000-byte outline threshold, with its serialized size reported on the notice. |

**Returns:** `meta`, a `kind` discriminator, one of two arms, and `next_cursor` on either arm while matched labels remain and openFDA's next link can be followed, on a page read at `skip` 0 or by cursor.

`kind: "full"` carries `results[]` — label records with structured sections: `indications_and_usage`, `warnings`, `dosage_and_administration`, `contraindications`, `adverse_reactions`, `drug_interactions`, `active_ingredient`, `inactive_ingredient`, `purpose`, `do_not_use`, `pregnancy_or_breast_feeding`, plus `openfda` enrichment (brand name, generic name, manufacturer, route, substance, pharm class, application number).

**Outline on overflow.** This is the one-document half of the shared [size contract](#response-size); the eight multi-row search tools cap `limit` per endpoint instead. A single SPL record runs to tens of thousands of tokens — a warfarin label is ~130 KB across 36 top-level keys, of which ~39 KB is `*_table` SPL table markup (measured 2026-07-26). The tables are not generally restated in the adjacent prose: warfarin's genotype dosing grid and trial results exist only in table form. Trimming only `format()` would desync `content[]` from `structuredContent`, so the size lever is caller-driven instead, via the framework's `outlineOnOverflow` helper (`@cyanheads/mcp-ts-core/utils`):

- With `sections`, each record is projected to the requested keys plus the always-kept metadata (`openfda`, `set_id`, `id`, `effective_time`, `version`) and returned as `kind: "full"`. A name no record on the page carries is reported on `enrichment.notice`, as a code literal — with the names the page does carry when nothing matched at all, since a typo and a genuinely absent section otherwise produce the same metadata-only record. A projection over the budget is returned whole and reports its serialized size on the same notice.
- Without `sections`, the page is measured against the helper's 24,000-byte budget. Under it, the records come back whole. Over it, the response is `kind: "outline"` with `outline[]` — every section name present on the page and its serialized size, largest first — `page_labels[]`, one entry per record on the page in page order (`set_id`, `effective_time`, `brand_name`, `generic_name`, `manufacturer_name`, `is_original_packager`, `bytes`; the three names and the flag are `null` on a label whose `openfda` block is empty), and the re-call guidance on `enrichment.notice`. The re-call is stateless: the same page inputs plus `sections` reproduce the records and slice them. The notice names each input the call set that chooses which labels the page holds — `search` always, then `sort`, a `limit` other than the default 5, a `skip` above 0, and `cursor` on a page read by cursor (`the same search, limit, and skip`) — since a re-call that drops one reads different labels. A label whose own `bytes` exceed 24,000 outlines even when re-called alone by `set_id`; `sections` then selects from it.

Every size this tool reports — `outline[]` entries, the worked example's figure, a selection's size — is UTF-8 bytes of the serialized JSON, as the search tools' oversized-record disclosure measures it; label text is often non-ASCII, where JavaScript string length undercounts the bytes on the wire. The whole-or-outline threshold itself is the helper's, which measures string length, so a page whose string length fits the budget comes back whole even when its multi-byte text takes it over the budget in UTF-8 bytes.

**Sizes are per page, not per record, so the guidance is measured rather than asserted.** An `outline[]` entry sums its section across every record on the page, so a section's retrieval cost is a function of `limit` and cannot be read off the section alone. The re-call guidance therefore projects candidate sections at this page's record count and names the largest one that measures within the budget, quoting that byte figure inline — following the notice returns exactly what it claims. Two candidates are skipped: the always-kept metadata keys, which ride every response, and the page's single most expensive section, since offering it as the worked example would recommend the one re-call the outline exists to head off. When metadata alone clears the budget — 40 metformin records carry ~31 KB of it — no example can fit, and the notice says so and points at `limit`.

**A brand or generic search matches repackagers' copies.** `openfda.brand_name:"<brand>"` matches the original packager's label and every repackager's copy of it. A page that leaves matched labels unreturned says how to read on — `next_cursor`, a `skip` while the next page stays within the ceiling, and past it a walk from `skip: 0` — and names two routes to the original packager's label: add `AND openfda.is_original_packager:true` to the `search` (openFDA stores the flag only as true, so the search keeps the labels it flags, and several or none can remain; this route is left out when the search already names the flag), or take `identity.spl_set_id` from `openfda_drug_profile`.

**Decision — an outline page names its records.** An `outline[]` entry sums its section across the page and names no record, so a caller could not tell the original packager's label from a repackager's copy, nor re-read one by `set_id`. `page_labels[]` lists each record's identity from its `openfda` block, with its own serialized size as `bytes`, measured as the outline entries are.

**Decision — the outline arm is a deliberate default-path change.** Before this, a `structuredContent` reader always got the complete label for any query that matched. Complex prescription drugs overflow the budget by 5-10x, so those queries now return an outline until the caller names sections. Bounding the default payload is the point: the alternative (one-sided `format()` truncation) hid the same data from `content[]` clients while claiming completeness.

**Decision — `*_table` sections render as Markdown tables in `content[]`, raw in `structuredContent`.** openFDA ships each `*_table` value as SPL table markup — `<table>`, `<content styleCode>`, `colspan`/`rowspan`, numeric entities — about 73% markup by character count. `format()` renders each string as a GFM pipe table (`src/mcp-server/tools/spl-table.ts`): entities decoded, spans expanded to a rectangular grid with the value in its origin cell, the caption above, `<tfoot>` rows and `[^n]:` footnote definitions below (numbered in one sequence across every table, section, and record in the response, so no label repeats; footnote IDs stay scoped to their table), `<sup>`/`<sub>` kept as `^`/`_`, and paragraphs or list items inside a cell joined by `<br>`. Markup that does not parse as balanced falls back to its decoded text. `structuredContent` keeps the provider string so the outline and selection byte figures measure what the caller receives there, and prose sections are never touched — some carry literal angle-bracket text (`<E050800>` in `inactive_ingredient`) that a markup pass would delete. No framework utility decodes SPL entities or renders these tables without optional peers, so the renderer is a small in-repo tokenizer with no new dependency.

**Decision — an over-budget `sections` selection is disclosed, never trimmed.** The selection path is the caller's own size decision, so it stays unconditional: `kind` remains `"full"`, every requested key is returned whole, and no content is stripped. What it adds is honesty about cost — the serialized size on `enrichment.notice`, which reaches `structuredContent` as `notice` and `content[]` as the enrichment trailer, so neither surface can read as in-budget when it isn't. Truncating or restructuring that arm to fit the budget would trade one silent failure for another: a caller who asked for `clinical_pharmacology_table` across ten records is asking for ~203 KB, and the useful answer is the payload plus its price, not a shortened payload.

### `openfda_search_drug_approvals`

Use to check if a drug is FDA-approved, find approval dates, review priority status, explore a sponsor's portfolio, find the patents and exclusivities on a product and its therapeutic-equivalence code, or read why FDA declined an application.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `dataset` | `"drugsfda"` \| `"orangebook"` \| `"crl"` | No | Default `drugsfda`: Drugs@FDA applications (`drug/drugsfda`), each with its sponsor, products, and submission history. `orangebook`: Orange Book product records (`drug/orangebook`), one per strength, with `patents[]`, `exclusivity[]`, and therapeutic-equivalence codes. `crl`: Complete Response Letters (`transparency/crl`), each with its full text. |

A path no record on the page carries is named on the notice. Omit for whole records. See [Field selection](#field-selection-fields). |

**Returns:** `meta` + records of the selected dataset + `next_cursor` on a page read at `skip` 0 or by cursor while records remain and openFDA's next link can be followed. `format()` never sees the input, so it routes on record shape: a `letter_date` marks a letter, a top-level `product_number` an Orange Book product, anything else a Drugs@FDA application.

- **Drugs@FDA application:** `application_number` (NDA, ANDA, or BLA), `sponsor_name`, `submissions[]` (type, status, status date, review priority, class code; each with `application_docs[]` of `id`, `url`, `date` as `YYYYMMDD`, and `type`), `products[]` (including `brand_name`), plus `openfda` enrichment on harmonized applications only (brand name, generic name, manufacturer, route, substance, product type). `submissions.submission_class_code:"TYPE 1"` selects new molecular entities.
- **Orange Book product** (one record per strength): `product_number`, `approval_date` (`YYYYMMDD`; `approved_prior_to_1982: true` stands in for it on an older product), one `products[]` entry (`application_type` `N` for an NDA or `A` for an ANDA, `application_number` as six digits with no prefix, `brand_name`, `active_ingredients[]`, `therapeutic_equivalence_codes`, `reference_listed_drug`, ...), `patents[]` (`patent_number`, `expiration_date`, `patent_use_code`, ...), and `exclusivity[]` (`exclusivity_code`, `exclusivity_expiration_date`). Most records carry no patents or exclusivity. No `openfda` block.
- **Complete Response Letter:** `application_number[]`, `letter_date` (stored `MM/DD/YYYY`, queried as `YYYYMMDD`), `letter_type`, `approval_status`, `company_name`, `company_address`, `approver_name`, `file_name`, and the letter's full `text`. One PDF can hold several letters, so a letter is identified by `application_number`, `file_name`, and `letter_date` together. `content[]` renders the address and the text as code literals, fenced when they hold line breaks, so a CommonMark parse reads them back exactly. No `openfda` block.

An application number is spelled once per dataset: a letter's `NDA 210274` is Drugs@FDA's `NDA210274` and the Orange Book's `products.application_number:"210274"` with `products.application_type:"N"` (`"A"` for an ANDA). A letter matches only its whole stored spelling: a wildcard reaches the prefix before the space (`application_number:NDA*` matches every NDA letter) and never the number (`application_number:2102*` and `"NDA 2102*"` match nothing).

**Cross-entry notice.** A matched Drugs@FDA or Orange Book search whose AND-ed clauses fall under one array carries a notice with the per-entry SQL, inline and staged alike: the arrays are `submissions`, `submissions.application_docs`, `submissions.submission_property_type`, `products`, and `products.active_ingredients` on Drugs@FDA, and `products`, `products.active_ingredients`, `patents`, and `exclusivity` on the Orange Book ([Clauses on one array](#implementation-notes)). A Drugs@FDA staged table holds `submissions` and `products` as `JSON` columns, the nested arrays inside them. An Orange Book record holds one `products` entry, so two fields of `products` raise nothing, while a pair under `products.active_ingredients` does, its SQL unnesting `t.products` and then the ingredients. Letters carry no array of objects and never raise it. On a page read by cursor the notice says to call again without `cursor` and with `stage: true`.

**Decision — one tool serves three datasets, selected by `dataset`.** The Orange Book and the Complete Response Letters answer approval questions Drugs@FDA cannot (what patents and exclusivities protect a product, which products are therapeutically equivalent, why an application was declined). The three share every input and differ only in endpoint, default sort, page size, identity keys, staged columns, and renderer, so a selector keeps one tool where three would repeat the same inputs. `dataset` defaults to `drugsfda`, which keeps every call that omits it unchanged. The `openfda` block is absent from Orange Book and letter records, so `openfda.*` searches belong to Drugs@FDA only.

## Response size

A response the caller cannot hold is not a successful response. openFDA payload size is driven by the upstream record shape, not by anything the caller can see in advance: a `drug/event` report averages ~30 KB (30,091 bytes over 1,000 reports from five searches; 11–62 KB by search, median ~6.8 KB, largest measured ~591 KB; measured 2026-11-10), a single `device/recall` record can exceed 4 MB (one serial-number list in `code_info`), while a `food/event` report is ~440 bytes, so one `limit` spans three orders of magnitude across the surface. `limit` is the page size and nothing trims a page below it, so the response is bounded by a per-endpoint cap on `limit`, set from measured record sizes; a record too large to inline on its own is disclosed rather than cut. `openfda_get_drug_label`, whose payload is one document, uses the framework's 24,000-byte `DEFAULT_OUTLINE_BUDGET_BYTES` as its overflow threshold, and the same figure marks a record oversized on the search tools.

The bound differs by the payload's shape, because the two record-bearing shapes have different escape hatches:

| Shape | Tools | Technique |
|---|---|---|
| One large document | `openfda_get_drug_label` | Section outline plus a stateless `sections` re-call — see [Outline on overflow](#openfda_get_drug_label) |
| Many rows | the eight multi-row search tools | Per-endpoint `limit` default and cap, disclosure of an oversized record, a `fields` projection for records too large to shrink by count, and the heaviest paths of three endpoints left out of a default page and returned through `include` (below) |
| Aggregate | `openfda_count_values`, `openfda_describe_fields` | Not measured — a term-count pair and a field entry are fixed-width, so `limit` alone prices the response (1000 terms is ~44 KB, the default 100 is ~4 KB). A date count's upstream read ignores `limit` (up to ~865 KB, `drug/drugsfda` `submissions.submission_status_date`, 15,310 buckets); ranking it costs ~13 ms of CPU, JSON parse included, and the response is still cut to `limit`. |
| Composed / caller-shaped | `openfda_drug_profile`, `openfda_dataframe_query` | Not measured — a profile is a fixed set of bounded sections, and a SQL result is the caller's own projection |

### Page size and oversized records (many rows)

`limit` is the page size: a page holds `limit` records, fewer only at the end of the match. Each endpoint has a default and a cap (`PAGE_SIZES` in `src/mcp-server/tools/schema-utils.ts`; `pageLimit` and `pageLimitBy` build the `limit` input, `resolvePageSize` applies it):

| Endpoint | Default | Cap |
|---|---|---|
| `drug/event` | 5 | 25 |
| `drug/label` | 5 | 1000 |
| `drug/enforcement`, `food/enforcement` | 25 | 1000 |
| `device/enforcement` | 10 | 125 |
| `device/recall` | 10 | 50 |
| `drug/drugsfda` | 25 | 375 |
| `transparency/crl` | 5 | 75 |
| `device/510k` | 10 | 175 |
| `device/pma` | 25 | 575 |
| `device/classification` | 25 | 600 |
| `device/event` | 10 | 175 |
| `food/event`, `cosmetic/event` | 25 | 1000 |
| `animalandveterinary/event` | 25 | 450 |
| `drug/orangebook`, `drug/shortages`, `tobacco/problem`, `drug/ndc`, `other/nsde` | 25 | 1000 |
| `count` (`openfda_count_values` terms) | 100 | 1000 |

A cap is the median record count that serializes to about 1 MB, rounded down to a multiple of 25, or openFDA's own 1000-record page maximum where a full page is at most 1.27 MB; measured 2026-11-10 through each tool's `format()`, as `structuredContent` UTF-8 bytes on 2–10 windows per endpoint. `drug/event`'s 25 sits between its product-search (~18) and all-window (~50) medians. A default stays well under its cap: 25 for short records, 10 or fewer for heavy ones, 5 for drug reports and labels. The tools that pick their endpoint from another input (`category`, `category` and `endpoint`, `pathway`, `dataset` on the approvals tool) list each selector's pair on `limit`.

A `limit` above the cap is clamped to it by default, with a notice naming the requested value, the cap, and where the next page starts (or that the page ends the match, or that the next page would pass the `skip` ceiling and that `next_cursor`, or a walk from `skip` 0, reads past it), one log line, and one `openfda.limit.clamped` counter increment. With `OPENFDA_CLAMP_LIMITS=false` the schema advertises the cap as `maximum` and a larger value fails before any request; on a multi-endpoint tool a value between the selected endpoint's cap and the tool's largest cap raises `limit_above_cap`. `meta.limit` reports the page size applied.

Every size is UTF-8 bytes of the serialized JSON — the size on the wire, not JavaScript string length, which undercounts multi-byte text (one device recall's `code_info` holds over 529,000 non-ASCII characters). `src/services/openfda/page-budget.ts` discloses a page whose records, as cut for the caller, include one that serializes above 24,000 bytes on its own — a by-ID lookup, `limit: 1`, a `drug/event` report listing dozens of drugs, a `device/recall` record whose `code_info` the call asked for. `page_bytes` reports the page's size, `page_largest_fields` carries the largest record's largest fields by dotted path and serialized size (array elements totalled into one path, so `patient.drug.openfda` across all of a report's drugs), and the notice, `enrichment.notice` and a `content[]` line alike, names them with the `fields` re-call that would shrink the record. The path drills to the deepest field that alone holds the excess — `patient.drug.openfda`, not `patient`, which a caller cannot leave out without losing the reactions it came for; when no single field holds it, the largest top-level fields are listed (at most three) until they do. Presence rule: `page_bytes` and `page_largest_fields` appear together, only when a record on the page exceeds 24,000 bytes; a page whose records each fit returns exactly `{ meta, results }`.

**Decision — output size is the caller's `limit`, not a byte budget.** A byte budget on each page was rejected: it overrides an explicit `limit` with a record count the caller cannot predict, and continuation stops being `skip + limit`. Record size spans three orders of magnitude across endpoints, so the bound sits where it can be set per endpoint: the cap on `limit`. A caller sees the cap on the input schema (or in the clamp notice), gets the page it asked for up to it, and pages on with `skip + limit`.

**Decision — a single oversized record is returned whole, and its size is stated.** Lowering `limit` cannot shrink one record, and trimming *within* a record unasked would either desync `structuredContent` from `content[]` (both derive from the same array) or hand back a record whose missing fields are indistinguishable from openFDA's own sparsity. The caller-requested `fields` projection (below) is the way to a smaller record. Replacing an oversized record with a field outline, the `openfda_get_drug_label` pattern, was rejected: it would put `results: []` in `structuredContent` for a real match, change the default response, and still need `fields` for the re-call.

**Decision — the oversized record is measured once and the breakdown rides the response.** `format()` receives a schema-parsed copy of the result and no context, so it cannot read the handler's notice; re-measuring there walked a multi-megabyte record a second time. `oversizedRecordFields()` measures it once and carries the result as `page_largest_fields`, and both the notice and the `content[]` line render from that field.

**Decision — the page is measured, the drain is estimated.** [DataCanvas staging](#datacanvas-staging-analytical-sql) derives its row cap from an average taken over a 100-row probe, because the rows it bounds have not been fetched yet. The inline page is already in hand, so a record on it is measured exactly: `drug/event`'s median record is ~6.8 KB against its ~30 KB mean, so an average would misjudge which pages hold an oversized record. The two measures are deliberately separate — ~16 MB for the drain, 24,000 bytes for one record — because one feeds a SQL table and the other flags a record too large for a context window.

### Field selection (`fields`)

Each of the eight multi-row search tools takes an optional `fields`: dotted record paths (`receivedate`, `patient.drug.medicinalproduct`). `src/services/openfda/record-projection.ts` projects each record to those paths plus its identity key before an oversized record is looked for, so the disclosure measures what the caller receives, and both surfaces carry the same projected records. Without `fields`, records come back whole, less the paths a default page leaves out ([below](#paths-left-out-of-a-default-page-include)).

| Tool | Identity key(s) kept on every projected record |
|---|---|
| `openfda_search_adverse_events` | `safetyreportid` (drug), `report_number` (food, device, cosmetic), `mdr_report_key` (device) |
| `openfda_search_recalls` | `recall_number` (enforcement), `product_res_number` (device recall) |
| `openfda_search_drug_approvals` | `application_number` (Drugs@FDA); `products.application_number`, `products.application_type`, `product_number` (Orange Book); `application_number`, `file_name`, `letter_date` (letters) |
| `openfda_search_device_clearances` | `k_number` (510(k)), `pma_number` + `supplement_number` (PMA), `product_code` (classification) |
| `openfda_search_animal_events` | `unique_aer_id_number` |
| `openfda_search_drug_shortages` | `package_ndc` |
| `openfda_search_tobacco_reports` | `report_id` |
| `openfda_lookup_ndc` | `product_ndc` (Directory), `package_ndc11` (NSDE) |

- A path through an array applies to every element, and the array keeps its length: an element carrying none of the requested paths stays as `{}` (`[]` for a nested array), so a report's drug count survives projection. An array no element of which carries the path is absent, like any missing key. A shorter path covering a longer one keeps the whole subtree.
- Each entry must be letters, digits, underscores, and dots with no leading, trailing, or doubled dot — advertised as the `pattern` on every array item, so a malformed path fails argument validation before any upstream request. An empty list is the same as omitting it.
- A path no record on the page carries is named on the notice (`enrichment.notice` and a `content[]` line), as a code span like every requested path the notice lists, never thrown: openFDA records are sparse, so absence from one page is not proof of a typo — the same rule `openfda_get_drug_label`'s `sections` follows.
- The response carries `projected_fields` (the requested paths) only when the call projected; a call without `fields` returns the shape it always has.
- With `stage: true`, `fields` shapes only the inline page; the drain stages whole records into the table's own column projection.

**Decision — projection is server-side and caller-requested.** openFDA has no field selection: the documented query parameters are `search`, `sort`, `count`, `limit`, and `skip`, and `fields=`, `_source=`, and `_source_includes=` each answer HTTP 400. So the full page is fetched and cut after. An include list was chosen over an exclude list because it is bounded by construction — excluding `more_code_info` from a device enforcement record still leaves tens of kilobytes of `code_info`.

**Decision — a projected record renders under its identity heading, field by field.** Each tool's curated `content[]` renderer routes on record shape (`patient` vs `device` in adverse events, `product_res_number` in recalls) and fills absent fields with `N/A` or `Unknown`; a projected record would land in the wrong branch or render a projected-away field as a placeholder the response cannot back. A projected record instead renders as `### <identity key>: <value>` followed by every field it holds, verbatim, and nothing else.

**Decision — the path pattern is a flat character class with lookaheads.** `^(?!\.)(?!.*\.\.)(?!.*\.$)[A-Za-z0-9_.]+$` accepts exactly the strings the nested `^[A-Za-z0-9_]+(?:\.[A-Za-z0-9_]+)*$` does, but stays linear on Bun's JavaScriptCore engine, where the nested form's backtracking cost on a long `a.a.a.` run with no valid end jumps roughly sixtyfold between 80,000 and 320,000 characters. The pattern runs over caller-supplied text.

### Paths left out of a default page (`include`)

A page read without `fields` leaves named heavy paths out of each record on three endpoints (`LEFT_OUT_BY_DEFAULT`, `src/services/openfda/record-projection.ts`); every other endpoint's default page keeps whole records.

| Endpoint | Tool | Left out |
|---|---|---|
| `drug/event` | `openfda_search_adverse_events`, `category: "drug"` | `patient.drug.openfda` |
| `device/enforcement` | `openfda_search_recalls`, `category: "device"` | `code_info`, `more_code_info` |
| `device/recall` | `openfda_search_recalls`, `category: "device"`, `endpoint: "recall"` | `code_info`, `openfda.k_number`, `openfda.fei_number`, `openfda.registration_number` |

- `include` takes dotted paths in the `fields` grammar. A left-out path named in `include` comes back whole; a path beneath one (`patient.drug.openfda.brand_name`) brings back that field alone. An entry naming no left-out path changes nothing. With `fields`, no default cut applies and an `include` entry naming a left-out path joins the projection.
- A `search` clause on a left-out path, or beneath it, counts as an include, so a caller filtering on `patient.drug.openfda.generic_name` gets the block it filtered on.
- `omitted_fields` lists each left-out path a record on the page lost, with the UTF-8 bytes it held across the page, in table order. It is absent when no record lost anything, and its notice, a `content[]` line, names the `include` re-call.
- The oversized-record disclosure measures the cut records, and a staged call cuts only its inline page: the drain stages whole records, left-out paths included.
- On `device/recall` the `openfda` lists cover every registrant and 510(k) of the product code, not the recall, so only those three lists are left out; its small scalars stay, `device_class` being the only class a device recall carries.

**Decision — the heaviest paths are left out of a default page and named.** Measured 2026-11-22, `patient.drug.openfda` is 92% of a `drug/event` page, `code_info` and `more_code_info` 89% of a `device/enforcement` page, and `code_info` with the three product-code lists 78% of a `device/recall` page; every other endpoint's default page stays under 85 KB. The drug is already named by `medicinalproduct` and `activesubstance`, and device `code_info` is a lot and serial list. Lowering `limit` cannot shrink one such record. The cut is the one the whole-record rules above rejected when unasked, and it differs in being declared: `omitted_fields` names each path with its bytes, so a missing block is distinguishable from openFDA's sparsity, and `include` returns it in one call.

## DataCanvas staging (analytical SQL)

**Gated twice over.** The deployment provides the surface with `CANVAS_PROVIDER_TYPE=duckdb`, the default (requires the `@duckdb/node-api` dependency; unavailable on the Workers runtime, where it fails closed at init), and the caller asks for staging per call. Without both, a search issues exactly one upstream request and returns one page — identical to a deployment with no canvas at all.

Every multi-row search tool — `openfda_search_adverse_events`, `_recalls`, `_drug_approvals`, `_device_clearances`, `_animal_events`, `_drug_shortages`, `_tobacco_reports`, and `openfda_lookup_ndc` — carries:

- `stage` (boolean, default `false`) — stage the matched set for SQL. Passing a `canvas_id` implies it, so successive searches accumulate onto one canvas for cross-table joins. The `canvas_id` input is declared with `CanvasIdSchema` (10 URL-safe characters, advertised as a `pattern`), so a value that could never be an id fails argument validation instead of reaching the canvas registry.
- Output fields `canvas_id`, `canvas_table`, `spilled`, `staged_rows`, `truncated`, `truncated_by` (all absent unless the call staged; `truncated_by` is present exactly when `truncated` is, and is one of `size_budget`, `row_ceiling`, `time_budget`, `upstream_end`). A staged call never returns `next_cursor` and refuses a `cursor` as `invalid_cursor`: its inline window is the probe or a `skip` page, never a cursor walk, though the drain itself may walk by `search_after`.
- Error reasons `canvas_disabled`, `canvas_not_found` (a well-formed `canvas_id` that expired or was never minted), and `canvas_capacity_exhausted` (`RateLimited`, retryable — a mint with `canvas_id` omitted at the per-tenant canvas cap). The last two come from the framework's `canvas.acquire()`; `canvas_id_malformed` is undeclared because `CanvasIdSchema` rejects a malformed id first.

**Decision — every staging surface names `openfda_dataframe_describe` before `openfda_dataframe_query`.** The staging notice, the `content[]` staging line, the `stage` and `canvas_table` descriptions, and each staging tool's `description` point at describe first. The inline page renders nested blocks (`openfda.brand_name`, `products[].marketing_status`) that are not canvas columns, so SQL written from the page without the column list fails as `invalid_query`.

`limit`/`skip` mean the same thing in both modes: a window over the matched set, served from the drain's first page when it covers the window and fetched directly otherwise, with the same [per-endpoint page size](#page-size-and-oversized-records-many-rows) and the same oversized-record disclosure. A staged call therefore never disagrees with an unstaged one about whether records exist at a given offset, about how many records a window holds, or about `meta.limit` — the page size applied, after any clamp. A [`fields`](#field-selection-fields) projection applies to that inline page only; the drain stages whole records.

**Bounded drain.** Staging drains from offset 0 until whichever comes first: a ~16 MB serialized-JSON budget (`STAGE_MAX_BYTES`), the end of the match, or a 50 s time budget (`STAGE_DEADLINE_MS`) counted from the call's start. The byte budget is converted to a row cap and a page size from a 100-row probe, because record size spans three orders of magnitude across endpoints — a `drug/shortages` row is ~1 KB, a `drug/event` report ~30 KB on average (11–62 KB by search) — so a flat row cap either starves the small endpoints or stalls the large ones. The time budget covers drain pages only: the probe and the inline page keep the service's own per-call deadline, so it ends a drain early with the rows already staged and never fails a call that stages. The drain walks by `search_after` when the probe's byte-derived row budget and `meta.total` both exceed 25,000, which openFDA's `skip` ceiling would otherwise cut; otherwise it walks by `skip`. Some walks openFDA cannot continue: a link carrying a sort key's missing-value marker, a continuation that fails through the service's retries (`query_error`, a 5xx, a rate limit, a 200 that is not openFDA JSON), or a link that repeats its page. Each goes on by `skip` from where it stands, up to 25,000 rows. `staged_rows` versus `meta.total` discloses exactly how much of the match reached the table, in `structuredContent` and in `content[]`; `truncated: true` when they differ, and `truncated_by` names what stopped the drain: `size_budget`, `row_ceiling` (the 25,000-row cap of a `skip` walk), `time_budget`, or `upstream_end` (openFDA served an empty or short page before its `meta.total`). The staging notice and the `content[]` staging line name the same cause. A truncated stage also names `openfda_count_values` in its disclosure: a `GROUP BY` over the staged rows describes only those rows, while a count query answers the same distribution over the whole matched set server-side in one request.

**Decision — `search_after` only past 25,000.** A drain whose rows fit under the `skip` ceiling sends exactly the requests it always did, so no existing stage changes its request pattern, ordering, or cost; only a match the ceiling would have cut walks by `search_after`.

**Decision — a failed continuation goes on by `skip`.** Every `search_after` request is one a `skip` walk never sends. Under 25,000 rows the fallback sends the `skip` page that walk would have sent, so the call fails only where that page fails too. Past 25,000 it ends the drain with every row walked, more than a `skip` walk stages, rather than failing a call the ceiling would have answered. A `skip` page that fails still fails the call.

**Decision — one deadline over drain pages only.** The probe and inline page are what a plain search already spends, so a deadline over them could fail a call that stages today. Bounding the drain alone makes the worst case a shorter table with `truncated_by: time_budget`, never an error; the 50 s sits below the 60 s request timeout MCP SDK clients default to.

**Canvas table shape.** Each endpoint registers an explicit, all-nullable column list with one column per top-level field its endpoint returns (`src/services/openfda/canvas-spill.ts` plus a per-tool schema constant; `src/mcp-server/tools/adverse-event-canvas-schemas.ts` for adverse events). The list is fixed per endpoint, never read off the matched rows, so two stagings of one endpoint share a column set and `UNION ALL`. Scalars are `VARCHAR` (openFDA returns most values as strings — `CAST` in SQL for numeric math) and nested objects and arrays (`openfda`, `patient`, `products`, `submissions`, …) are `JSON` columns read with DuckDB json functions. A field the endpoint does not send for a record registers as `NULL`. The drain feeds the raw records straight to the appender, which projects them onto the schema, so sparse, heterogeneous records ingest without NOT-NULL failures.

| Staged table | Columns |
|---|---|
| Adverse events: drug / food / device / cosmetic | 27 / 7 / 90 / 12 |
| Recalls: enforcement (every category) / device recall | 25 / 28 |
| Drugs@FDA applications / Orange Book / Complete Response Letters | 5 / 6 / 13 |
| Device clearances: 510(k) / PMA / classification | 24 / 24 / 17 |
| NDC Directory / NSDE | 22 / 12 |
| Animal events / drug shortages / tobacco | 20 / 19 / 9 |

- No staged adverse-event table has a top-level `openfda` column, since no adverse-event record carries one. The block is read from inside the nested column: `json_extract(patient, '$.drug[N].openfda')` on drug, `json_extract(device, '$[N].openfda')` on device. The drug arrays sit inside the `patient` column.
- A device report sends most of its fields on every record, as `''` when unset, so `IS NULL` misses them: test `= ''` or `NULLIF(col, '')`. 24 device columns held `''` on all 800 sampled reports.
- `reportduplicate` on a drug report is a `JSON` object on some reports and an array on others; `json_type` tells them apart.
- `therapeutic_category` on a shortage stages as one comma-joined `VARCHAR` (`Rheumatology,Oncology`), which `LIKE` and `=` read as a text value; no category name holds a comma.
- A letter's `application_number` and `approver_center` are `JSON` lists, and its `letter_date` stays as stored, `MM/DD/YYYY`.

**Decision — a staged table holds every top-level field its endpoint returns.** A field outside the table cannot be reached by SQL though the inline page shows it, and a column set that followed the matched rows would not union with the next staging of the endpoint.

**Decision — `openfda_search_recalls` stages each endpoint shape against its own projection, and each projection is every top-level field its endpoint returns.** Enforcement records (every category) stage all 25 enforcement fields, `code_info` (affected lots and expiry dates) and `more_code_info` among them: openFDA cuts `code_info` at 32,600 characters, mid-token, and continues the list in `more_code_info`, so both stage verbatim and `code_info || coalesce(more_code_info, '')` recovers the whole list. The termination and center-classification dates, the initial firm notification, and the firm address stage too. `product_code` and `res_event_number` are not staged for enforcement — no drug, device, or food enforcement record carries either (`_exists_:` answers 404 on all three), so a filter on them would silently match nothing. `device/recall` records stage every top-level field the endpoint returns — `product_res_number`, `recall_status`, `res_event_number`, `root_cause_description`, the four `event_date_*` fields, firm address and contact, `code_info`, `action`, with `k_numbers`, `pma_numbers`, and `openfda` as `JSON` — and none of the enforcement-only columns, which would always be `NULL` there. Staging device recalls against the enforcement projection dropped their identity and status from the table.

## Local bulk mirror

**Opt-in, off by default.** `OPENFDA_MIRROR_ENABLED=false` is the shipped posture and short-circuits before anything opens: `OpenFdaService.query` is the live client and nothing else. Enabling it adds a local-first read path for four datasets; every other endpoint and every ineligible query is untouched.

### Why a mirror, and why this narrow

openFDA allows 240 req/min and 120K/day with a key (1K without). Bulk and repeated-lookup workflows exhaust that, and any 429 blocks every tool. openFDA also publishes whole-dataset JSON dumps at [open.fda.gov/data/downloads](https://open.fda.gov/data/downloads/) with the same record schema the API returns, so a local copy is exact for the records it holds.

**Decision — the mirror answers exact-key lookups only; everything else routes live.** A sibling server in this fleet shipped an equivalent local index and then removed it: openFDA's `search` runs server-side in Elasticsearch, which tokenises and ranks, and a local corpus diverged from live on match counts and result ordering. The gate in `src/services/openfda/mirror/query.ts` keeps the mirror to the class of queries where a SQL equality test provably selects the same documents as the upstream phrase query. All four conditions must hold:

1. the search is a single quoted `field:"value"` term — no boolean operators, wildcards, ranges, or second clause. (Quoting matters: `recall_number:D-321-2016` matches 17,798 documents upstream where `recall_number:"D-321-2016"` matches one, because openFDA's analyzer splits the unquoted term at its hyphens and ORs the parts. A caller's unquoted hyphenated value arrives quoted, so it routes like its quoted form.)
2. the field is declared in the dataset's `keys` and the value matches its canonical grammar, **case-sensitively**. openFDA's analysed index is case-insensitive; the stored literal is not, so `application_number:"nda017398"` routes live rather than returning a false miss.
3. no `count`, no `sort`, `skip === 0`, and no `search_after` continuation. Aggregation, ordering, and walk position are upstream's to define: a mirror a refresh cycle behind can hold one record where live holds two, and would answer a continuation with page one again.
4. the value matches exactly one record. A single record has no order, so a mirrored answer is byte-identical to the API's rather than merely set-equivalent.

**Decision — a multi-record match routes live, narrowing the original page-fits rule.** The first cut of the gate served any match set that fit the requested page, reasoning that a complete set loses nothing but position. It does lose something: openFDA returns an unsorted match in its own index order, so `results[0]` and the whole `content[]` rendering differed between mirror and API for the three non-unique keys — a divergence a caller cannot detect. That order is server-side and not derivable from the dumps, so the options were to reproduce it (impossible), document it (leaves the hazard in place), or narrow the gate. Narrowing makes the divergence structurally impossible and costs only multi-record lookups. Of the distinct key values in the mirrored corpora, 98.6% of `product_ndc` (133,095 of 134,993) and 69.2% of `event_id` (3,195 of 4,618) address exactly one record and still serve locally. `set_id` is declared non-unique as a conservative posture but is not one in practice — openFDA indexes one current record per SPL set, so across all 260,986 `drug/label` records the most-frequent `set_id` occurs once, and no `set_id` lookup is affected. The keys that lose coverage are the two whose multi-record case is the point of the query: an `event_id` names a recall *event*, and a `product_ndc` with several package configurations lists them all.

**Decision — `openfda_count_values` is never mirrored.** A partial or one-cycle-stale mirror returns a plausible but incomplete tally with no detectable miss, which is worse than a slower correct answer.

### Scope

| Dataset | Primary key | Additional lookup key | Bulk dump |
|---|---|---|---|
| `drug/label` | `id` | `set_id` | 14 partitions |
| `drug/ndc` | `product_id` | `product_ndc` | ~27 MB compressed |
| `drug/enforcement` | `recall_number` | `event_id` | ~3.8 MB compressed |
| `drug/drugsfda` | `application_number` | — | ~9 MB compressed |

Out of scope: `drug/event` and `device/event` (FAERS size warrants its own effort), all device endpoints, food and cosmetic endpoints, `drug/shortages` (no bulk dump published), and the Orange Book (`drug/orangebook`), Complete Response Letters (`transparency/crl`), and NSDE (`other/nsde`), which `MIRRORED_ENDPOINTS` does not list, so a query on one routes live.

### GMDN licensing carve-out

openFDA data is dedicated to the public domain under CC0 1.0 with one exception: GMDN® Term Code, Term Name, and Term Definition are licensed from The GMDN Agency, and redistribution or AI-training use requires a separate licence. Those terms ride in the `gmdn_terms[]` block of the device UDI (GUDID) dataset, `device/udi`. `device/classification` records carry none: a classification's `definition` is the regulation's identification text, not a GMDN definition. Whether `device/classification` may enter the mirror is a separate licensing decision, so `MIRRORED_ENDPOINTS` stays closed to device data until it is made.

Two layers enforce the exclusion. `MIRRORED_ENDPOINTS` is a closed list of four drug datasets, so no device dump is reachable in the first place. `assertNoGmdnContent` is the backstop: every ingested record is walked for a GMDN-bearing key before it reaches the store, and a hit aborts the sync with the offending path named. An upstream schema change that starts emitting GMDN fields into a drug dataset therefore fails loudly instead of silently writing licensed content to disk. Any future extension to device data needs that licence cleared first.

### Sync model

openFDA publishes no incremental API for these endpoints, so **both `init` and `refresh` re-read every partition**; a refresh whose `export_date` has not advanced past the stored checkpoint returns without downloading anything. Each row carries the export date it was written from, so once every partition has been read the pass tombstones rows an older export left behind. The export date is published as the checkpoint only after the last partition — publishing it earlier would let a later refresh skip work an interrupted run never finished.

A partition is a single-entry ZIP whose JSON unpacks to hundreds of megabytes, so `bulk-stream.ts` holds neither whole: it parses the ZIP local header off the front of the response, inflates the rest through `DecompressionStream`, and runs a depth-aware scanner that emits `results[]` elements as they complete. The reader is strict about the layout openFDA publishes (single entry, deflate, sizes in the header, `results` array closed) — a best-effort parse of an unexpected archive would produce a silently partial mirror.

One SQLite file per dataset (`<slug>.db` under `OPENFDA_MIRROR_PATH`), because the framework's `mirror_sync_state` row is per database and the four datasets have independent lifecycles. A row is the primary key, the lookup columns, the dump's two freshness stamps, and the verbatim upstream record in `raw` — so a mirrored response returns the same JSON the API would. Records with no primary key are unaddressable and are skipped (`drug/enforcement` carries one).

### Lifecycle

**Init runs out-of-band, never at startup** — `bun run mirror:init [dataset...]`, backed by `scripts/openfda-mirror.ts` (`init` / `refresh` / `verify` / `status`). It is idempotent and resumable from the persisted cursor. Refresh is wired to `schedulerService` in `setup()` when `OPENFDA_MIRROR_REFRESH_CRON` is set and the transport is HTTP; a stdio server is a short-lived per-client process, so its operator runs `bun run mirror:refresh` from the host. The cron **skips** any dataset that has never completed an init rather than performing a multi-hour first harvest on a scheduled tick. It also skips a dataset whose store another process is already syncing: the SQLite store holds one sync lease per file, so a refresh that meets a running `mirror:init` records `skipped: 'sync-locked'` instead of a failure. Teardown stops a refresh in flight before it closes the stores: it aborts the pass, waits for the running dataset's run to settle (recorded as stopped and resumable, never as a failure), and starts no further dataset. `scripts/openfda-mirror.ts` initializes the framework logger (`stdio`, JSON lines on stderr) before it runs.

### Fallback

The read path gates on the framework's durable completion marker (`mirror.ready()`), which stays true through a refresh, so a mid-refresh or last-refresh-failed mirror keeps serving. `OPENFDA_MIRROR_FALLBACK_LIVE` (default `true`) routes to the API when the mirror is cold, when the store itself fails, and — deliberately — when a lookup matches nothing: a zero-match on a mirror one refresh cycle behind is indistinguishable from a genuine miss, so the API arbitrates. Set it to `false` to raise instead, for a deployment that must not spend API budget.

**`meta.lastUpdated` reports the mirrored dump's own stamp**, which can differ from the live API's for the same endpoint — the API index and the published dumps advance on separate schedules. Reporting the live value would misrepresent the vintage of the data actually being served.

## Implementation Notes

**Uniform query layer.** All 15+ openFDA endpoints share identical query mechanics: `search=field:value`, `count=field`, `sort=field:asc|desc`, `limit=N`, `skip=N`. The service layer should implement one generic query function parameterized by endpoint path, with tool handlers providing domain-specific defaults and output formatting.

**Decision — one Markdown cell escaper, escaping only what would change the rendering.** `openfda_dataframe_query` header and data cells, `openfda_count_values` terms, and the SPL table cells of `openfda_get_drug_label` all pass through `escapeTableCell` (`src/mcp-server/tools/format-utils.ts`). It escapes `|`, turns line breaks into `<br>`, and escapes emphasis, code, link, and strikethrough markers. A `\`, `<`, `&`, or `_` is escaped only where the next or surrounding character would change how it renders. A blanket escape would break text agents copy out of `content[]`: a column name like `recall_number` is the next SQL query's identifier, and `p<0.05`, `AT&T`, and `CARBIDOPA\LEVODOPA` all render as written. Bare web addresses are the one place an escape itself corrupts: GFM links `http://`, `https://`, and `www.` text from the raw source, so a backslash inside one shows in the link text and its href (`http://example.com/\~user`, a device recall's `…(2)\[3\].pdf`). An address that marked and micromark both link whole is emitted verbatim up to the whitespace or `<` that ends it: it must open where GFM allows (`www.` after whitespace, `(`, `*`, `[`, `]`, or `~`; `http(s)://` after anything but a letter, digit, `.`, `_`, `+`, or `-`, which an email autolink could absorb), carry a valid ASCII domain, contain no `|`, no `](`/`][`, and no `(` left unclosed, and end in nothing GFM trims but plain punctuation — a trimmed `*`, `_`, `~`, or `&name;` would render as Markdown or decode. An address that fails any of these and needs an escape has its opener's `:` or `.` escaped instead (`xhttp\://…`, `WWW\.…`, `ftp\://…`), so neither parser links it and its text renders exactly; one with nothing to escape stays byte-identical. A parser-backed fuzz over marked and micromark+GFM checks that every value renders as one cell holding its exact text and that every link's href matches its own text. SPL text is escaped one run at a time, with whitespace collapsed first, as a fragment: the next run follows it directly, so a trailing `<` or `\` is escaped and an address reaching the run's end is never kept as a link. Markup that does not parse as balanced falls back to its decoded text on one line, escaped the same way. A block marker that opens a caption, footer, loose-text, or fallback line (`>`, an ATX `#`, a `+` or `-` bullet, a setext underline, an `n.` or `n)` ordinal) is escaped so it cannot start a block and drop out of the rendered text. Outside tables, every single-line slot that carries upstream or caller text — record headings and titles, `**Label:** value` lines (each line `formatRemainingFields` emits included), the search lead lines, and list items — flattens CR, LF, and CRLF to a space (`singleLine`), so a value cannot open a heading, list item, or quote of its own. The `openfda_drug_profile` heading and resolution line are the exception: their caller values ride as code literals (next decision), and one holding a line break becomes a fenced block on the following lines. Where the value itself opens the line's content — a list item's text, the animal-details line of `openfda_search_animal_events` — `lineContent` also escapes a block marker it starts with: an ATX `#`, `>`, a bullet or ordinal, a thematic break, setext underline, or table delimiter row, a code fence, an HTML block, a link reference or footnote definition, or a task-list box. A value with no line break and no leading marker stays byte-identical, and only the `content[]` text changes; `structuredContent` keeps every value as openFDA sent it. Two places keep upstream line breaks on purpose: `openfda_get_drug_label` prose sections are the label's own multi-line text and render verbatim, with `*_table` sections going through the SPL renderer above; and enrichment notices, which the framework renders into the `content[]` trailer from the same string `structuredContent` carries.

**Decision — caller text in prose is a code literal, never escaped.** Caller text a notice interpolates — a `search`, a `count` field, a drug name, `sections` names, `fields` paths, a quoted phrase in the `+` hint — and caller text a `format()` renders into prose — the `openfda_drug_profile` heading's drug name and the fan-out key on its resolution line, the `canvas_id` and dropped `table` the dataframe tools echo — rides as a code literal (`codeLiteral` in `format-utils.ts`, built on the framework's `MarkdownBuilder.inlineCode()` / `.codeBlock()`): a one-line value as a code span whose backtick fence is one longer than the longest backtick run inside it, space-padded where CommonMark would strip or merge a character; a value holding a line break as a fenced block on lines of its own, which stays inside the notice blockquote because the trailer prefixes every line. Both surfaces carry the wrapped string, so the value between the delimiters is the caller's text byte for byte and a CommonMark parse reads it back exactly. A backslash escape is no substitute: in a Lucene query `\*` is a literal asterisk, so `openfda.brand_name:\*cillin\*` matches nothing where `openfda.brand_name:*cillin*` matches 566 labels. Server-authored notice text and upstream values (section names a page carries, field paths in the oversized-record notice) are unchanged. Caller text in a table cell (the SELECT aliases `openfda_dataframe_query` renders as header cells) stays on `escapeTableCell`: GFM splits a cell on `|` even inside a code span, so a code literal cannot carry such an alias exactly.

**Elasticsearch syntax quirks:**
- Boolean: `AND`, `OR`, `NOT` in uppercase (lowercase `and` is a term); clauses separated by a space are OR'd. openFDA's docs write a space as `+` because they show the URL; the tools send `search` form-encoded, so `searchExpression()` (`search-expression.ts`) turns a `+` into a space only in a separator position — beside a standalone `AND`/`OR`/`NOT`/`TO`, after a closing `"`/`)`/`]`/`}`, or between a term and the next `field:` — and leaves every other `+` as sent: a phrase-internal plus is data (`brand_name.exact:"Bausch + Lomb"` on `device/udi`), a term-final one too (`device_name.exact:Knee+` on `device/510k`), and a leading `+field:` is Lucene's required operator. In a query that uses that operator, a `+` before a clause stays the operator too (`+a:"x"+b:"y"` answers as AND).
- **OR on the enforcement endpoints.** `drug/enforcement`, `food/enforcement`, and `device/enforcement` share one index; openFDA appends its own product-type clause to `search`, so an ungrouped top-level `A OR B` matches only `B` (food `product_description:"cheese" OR product_description:"milk"`: 1,675 against a 3,141 union; drug `metformin OR lisinopril`: 41 against 132; device `catheter OR stent`: 356 against 2,964). The service sends every `search` inside one pair of parentheses (`buildUrl()` in `openfda-service.ts`), so OR is a union on every endpoint; queries with no top-level OR return the same total wrapped or not, verified on all 20 endpoints the search tools page. Echoes and the mirror gate keep the unwrapped string.
- Exact matching: field values in quotes (`"aspirin"`). Without quotes, tokenized matching.
- `.exact` suffix on count fields for whole-phrase aggregation vs. tokenized.
- Date ranges: `[20200101 TO 20201231]` (the URL form `[20200101+TO+20201231]` also works). `drug/shortages` is the exception on its four date fields (`initial_posting_date`, `update_date`, `discontinued_date`, `change_date`): they are stored `MM/DD/YYYY` and also accept epoch milliseconds, so a raw eight-digit `20261120` is read as a time on 1970-01-01. The tools send `YYYY-MM-DD` there, rewriting the other calendar forms (`src/mcp-server/tools/shortage-dates.ts`; [Dates on `drug/shortages`](#implementation-notes)).
- Wildcard: `field:aspir*`.
- `sort` takes a comma-separated list, not a single field: `report_date:desc,status.exact:asc` is a working multi-field sort. A bare field path with no direction (`sort=report_date`) sorts ascending, any whitespace around the whole value is trimmed, and so are spaces around a segment (`a:desc, b:asc` sorts identically to `a:desc,b:asc`). Only a lowercase `asc` or `desc` direction is honoured: `DESC`, `Desc`, `ascending`, `"desc"`, or an empty `field:` answers HTTP 200 with that key silently dropped — the unsorted order for a single key, the remaining keys' order in a multi-field sort — on all 20 endpoints the search tools page. The tools rewrite `asc`, `desc`, `ascending`, and `descending` in any letter case to the lowercase form and reject every other direction.

**Clauses on one array.** openFDA tests each clause of a `search` against the whole record, so AND-ed clauses on fields under one array of objects can be met by different entries (`submissions.submission_type:"ORIG" AND submissions.review_priority:"PRIORITY"` matches an application with an `ORIG` submission and, separately, a `PRIORITY` one). `src/mcp-server/tools/search-clauses.ts` reads the caller's `search` in Lucene's classic grammar and, for a matched search (total above 0), names the clauses that can split: two clauses on different fields (`.exact` dropped; `_exists_:` and `_missing_:` count on the field they name) under one array listed for the endpoint in `OBJECT_ARRAY_PATHS` (`field-catalog.ts`), both of which every match must satisfy as the classic parser reads their group: joined by `AND`, both required with `+`, or one of them prohibited beside a positive one. An `OR` elsewhere in the group does not free them: `a AND b OR c` reads as `+a +b c`, and openFDA answers it with the total of `a AND b`, so the pair still counts. Two clauses joined only by `OR` or by operator-less adjacency, the same field twice, two arrays, a top-level or plain-object field, or two negated clauses raise nothing. The notice names the array, its fields, and the staged route to one entry with its SQL condition: `call again with stage: true` on an inline page (`without cursor and with stage: true` on a page read by cursor), the table's own name on a staged call, and on `openfda_count_values` the endpoint's search tool, its selector input, and `stage: true`. The condition is an `EXISTS` over `unnest(from_json(<array column>, '["json"]'))` of the staged table aliased `t`, one nested `EXISTS` per array level, and an array inside a plain object is read from that object's column (`json_extract(t.patient, '$.drug')`). `drug/orangebook` records hold one `products` entry each (`SINGLE_ENTRY_ARRAYS`), so two fields of `products` raise nothing, while a pair under `products.active_ingredients` does. Eight endpoints are surveyed: `drug/drugsfda`, `drug/orangebook`, `drug/event`, `device/event`, `food/event`, `cosmetic/event`, `animalandveterinary/event`, `drug/ndc`; `transparency/crl` and `other/nsde` were read and hold none, and an endpoint absent from the table is unsurveyed, not claimed free of arrays.

**Decision — the per-entry answer is a notice with SQL, and every condition is a relaxation.** The server cannot make openFDA match per entry, but a staged table holds each array as a `JSON` column, so one SQL condition answers it. A term or phrase compares as a case-insensitive substring (`ILIKE`, or `LIKE` on an `.exact` field) rather than `=`, because a stored value can hold more words than the query and can be a list of strings; a numeric range compares numerically; `%` and `_` in a caller value stay SQL wildcards. Each is wider than openFDA's own match, never narrower, so the filter cannot drop a record that has one entry meeting every tied clause. The condition is an `EXISTS` over a subquery, never the lateral unnest form, which the read-only SQL gate refuses.

**Dates on `drug/shortages`.** `initial_posting_date`, `update_date`, `discontinued_date`, and `change_date` are stored `MM/DD/YYYY` and indexed as dates that also accept epoch milliseconds, so an eight-digit `20261120` is read as a time on 1970-01-01, a date that is not zero-padded matches nothing, and an unquoted `11/20/2026` parses as something other than a date. `YYYY-MM-DD` is read as written. A value written `YYYYMMDD`, `M/D/YYYY`, or `YYYY-M-D` is rewritten to `YYYY-MM-DD` (`src/mcp-server/tools/shortage-dates.ts`): a `field:` term, bare or quoted, and either bound of a `[…]` or `{…}` range; a rewritten bare term is sent quoted, as every unquoted hyphenated term is. `*`, epoch milliseconds, date-times, date math (`now-30d`), a date that does not exist (month 13, 30 February), a `field:(…)` group, a regexp, and every other field are left as written, and so is a query holding a refused character. It applies to `openfda_search_drug_shortages` and to `openfda_count_values` on `drug/shortages`; a raw unquoted `MM/DD/YYYY` anywhere else still misparses. When a search or count holding a group on one of the four fields matches nothing, the no-match notice names the group's field and says its dates are sent as written, so to write each one `YYYY-MM-DD` (`shortageDateGroupHint`).

**Decision — a shortage date is rewritten, not rejected.** Each of the three forms has one reading, and `YYYYMMDD` is what `openfda_count_values` returns for these fields, so a caller who counts dates and then filters by one would otherwise hit the epoch reading and get a silent wrong answer rather than an error.

**Query hygiene — two paths, two mechanisms.** A Lucene query reaching openFDA has one of two origins, and they need opposite treatment. The caller-written half lives in `src/mcp-server/tools/search-expression.ts` (`search`), `src/mcp-server/tools/schema-utils.ts` (`sort`), and `src/mcp-server/tools/shortage-dates.ts` (dates on `drug/shortages`); the tool-composed half in `src/mcp-server/tools/definitions/drug-profile.tool.ts`.

| Origin | Tools | Mechanism | Failure |
|---|---|---|---|
| **Caller-written Lucene** — the caller authored the query and owns its syntax | the ten tools taking a `search` and/or `sort` input | **Reject** what is provably malformed, before the request; **normalize** what has one reading: whitespace and URL-form `+` separators read as spaces, an unquoted hyphenated term sent quoted, and on `drug/shortages` a date rewritten to `YYYY-MM-DD` (`searchExpression()`, `rewriteShortageDates()`) | `malformed_search` for `search`; a schema `ValidationError` for `sort` |
| **Tool-composed Lucene** — the tool built the query from a caller-supplied *term* | `openfda_drug_profile` (every clause off one `drug` name) | **Read** the term once (each run of whitespace and refused characters becomes one space), then **escape** it for the phrase context it lands in | none for a name holding a letter or digit — every such term produces a well-formed query; `blank_drug_name` otherwise |

Philosophy: **reject what is provably malformed locally; let openFDA arbitrate what is merely unknown; and never make the caller answer for a query they did not write.** Where the reject line falls is decided by the upstream's own answer, probed against `api.fda.gov` value by value: every value either mechanism refuses is one openFDA refuses outright or answers with silently wrong data (a trailing backslash, an unhonoured `sort` direction), with the single recorded exception under [Out of scope](#out-of-scope-deliberately).

### Caller-written: reject

`search` and `sort` were declared as any non-blank string, so a value that cannot be valid still cost a network round-trip and came back as a raw Lucene/Elasticsearch message — a lexer column index past the end of the submitted string, or a mapping error naming a token the caller never meant as a field.

| Input | Check | Where | Failure |
|---|---|---|---|
| `search` | No character openFDA refuses (checked first); quotes, parens, and range brackets each close; no trailing escape | `assertSearchDelimitersBalanced` (`src/mcp-server/tools/search-expression.ts`), first lines of each handler | `malformed_search`, naming the character and its position or the specific delimiter fault |
| `search` (normalized, not rejected) | Whitespace other than the space and a separator `+` read as a space; an unquoted hyphenated term is quoted; on `drug/shortages`, a `YYYYMMDD`, `M/D/YYYY`, or `YYYY-M-D` date becomes `YYYY-MM-DD` | `searchExpression()` on the schema (`.overwrite()`), so the handler, the staged path, and the echoed query hold the rewritten string; `rewriteShortageDates` on `openfda_search_drug_shortages`' schema and in `openfda_count_values`' handler | none; the rewritten form shows in the echoed query where the tool echoes one (`openfda_count_values` echoes none) |
| `sort` | Comma-separated `field-path[:direction]` groups, the direction `asc`/`desc`/`ascending`/`descending` in any case, normalized to lowercase `asc`/`desc` | `SORT_EXPRESSION_PATTERN` on the schema, so it reaches the advertised `inputSchema` as `pattern`; the normalization runs in the schema after it | Schema `ValidationError` showing the expected form |

**Decision — the `search` check is a three-context scanner, not a character count.** A delimiter means different things in different contexts, and a count is wrong in both directions:

| Context | Opened by | What the delimiters mean | Upstream evidence |
|---|---|---|---|
| Normal | — | `"` opens a phrase, `[`/`{` a range, `(`/`)` group | a `)` or `]`/`}` with no opener is refused; so is a bracket mid-term (`reason_for_recall:foo[bar` → `parse_exception`, since an unquoted `[` is always a range opener) |
| Phrase | `"` | every other delimiter is literal data | `product_description:"Packaged as a) 4 FL OZ"` (one `)`, no `(`) matches a real `drug/enforcement` record |
| Range | `[` or `{`, closed by `]` or `}` | same — literal data | `report_date:[(20200101 TO 20201231]` and `report_date:["20200101 TO 20201231]` are both answered, not refused |

A backslash escapes the next character in every one of the three, ranges included — openFDA answers `Term can not end with escape character` when one eats a range's closing bracket. `product_description:"foo \" bar"` is therefore a valid three-quote query, and `[X TO Y}` closes even though the brackets differ.

**Decision — a trailing backslash is rejected, because the alternative is silently wrong data, not an error.** A `\` at the end of the query has nothing to escape. On endpoints that scope a shared index openFDA appends its own clause, so the escape lands on that clause's leading space rather than on end-of-input: `recalling_firm:pfizer\` on `drug/enforcement` answers **HTTP 200 with 18856 records against 155** for `recalling_firm:pfizer`, because the swallowed space dissolves the appended `product_type:drugs` scope and the caller is served another product type's recalls. On an endpoint with nothing appended the same value is a `token_mgr_error` whose echoed tail is empty — the least actionable shape on the surface. Both are locally detectable from one character. `recalling_firm:pfizer\\` (an escaped backslash) is valid and returns the correct 155.

**Decision — a `sort` direction is normalized when its meaning is certain and rejected otherwise.** openFDA splits a sort segment on its **last** colon and validates only the left side, so any direction answers HTTP 200 — but only a lowercase `asc` or `desc` is applied. Every other token drops its key silently, measured as an order identity (not a status code) on all 20 endpoints the search tools page: `report_date:DESC` returns the same records as no sort, and `classification.exact:desc,report_date:ascending` returns `classification.exact:desc` alone. A 200 is therefore no evidence that a direction works, and no token outside the accepted set is ever applied, so rejecting one loses no working call. `asc`, `desc`, `ascending`, and `descending` in any letter case are accepted and rewritten to lowercase `asc`/`desc` by a Zod `.overwrite()` inside the schema, after the pattern accepts the value — so every handler and the staged path receive the honoured form, and the advertised `pattern` (which `.overwrite()` leaves unchanged) states exactly the accepted spellings. Anything else — `"desc"`, `foo`, an empty `field:`, a prefix like `asce` — is a schema `ValidationError` naming the directions. A colon must be followed by exactly one direction, which is also what makes `report_date:desc:asc` reject: openFDA would read its field path as `report_date:desc` and refuse it.

**Decision — the `sort` pattern is lookaheads over one character class, not a repeated segment group.** The grammar is `^\s*SEG( *, *SEG)*\s*$`, but written that way JavaScriptCore's backtracking cost on a long run of segments with no valid end grows several-hundredfold between 5,000 and 320,000 characters, and the pattern runs over caller-supplied text. The advertised form validates the character set with one character-class run and rules out each structural fault with a lookahead; a test pins it to the plain grammar over every string of up to five tokens, and a CPU-time test bounds its growth across a 64× span on Bun and on Node, each timed in a child process because vitest itself runs on Node.

**Decision — whitespace around the value and spaces around a segment are accepted; whitespace inside a segment is not.** openFDA trims the whole value of any whitespace (tabs, line breaks, and no-break spaces included — the set `\s` matches) and then the spaces around each segment before looking it up, so `classification.exact:desc, report_date:asc` returns the same ordering as the space-free form, and `  report_date:asc  ` and `report_date:asc\t` sort normally; a pattern without the allowance rejects a working sort written the way a caller naturally writes a list. Neither trim reaches inside a segment — `report_date :asc` fails upstream with `No mapping found for [report_date ]`, and a tab or no-break space beside a comma answers 400 — so the field path itself stays space-free.

**Decision — the `search` check is a handler guard, the `sort` check is a schema `pattern`.** `sort`'s grammar is regex-expressible, so putting it on the schema advertises it in `tools/list` and lets a client self-correct before spending a call. `search`'s balance test is not regex-expressible, and a schema-level rejection carries no `structuredContent.error.data.reason` and none of the declared recovery text — the same reasoning that keeps the pagination ceiling out of a schema `.max()`.

**Decision — a character openFDA refuses is rejected before the request, `^` and `~` included, and named with its position.** openFDA answers HTTP 400 `Search not supported` to a query holding `!`, `#`, `$`, `;`, `?`, `^`, `|`, `~`, the backtick, or any character outside printable ASCII that is not whitespace, anywhere in it, inside a quoted phrase and after a backslash alike. Its reply echoes the whole query, HTML-escaped, and never the character, and its recovery text points at field names and boolean operators, so the caller is left to find the one character by hand. The guard (`SEARCH_REFUSED_CHARACTER`, `search-expression.ts`) runs ahead of the delimiter scan and names the character (`U+XXXX` for a non-ASCII one, so an invisible or direction-changing character never lands in the message), its 1-based position, and the syntax that works instead: `NOT` for `!`, `OR` for `|`, `*` for `?`, nothing for `^` and `~`, which openFDA has no boost or fuzzy operator for. An accented letter is the one non-ASCII case with a spelling to offer: openFDA stores names unaccented, so a space or nothing in place of the `é` of `Néoral` matches no record, and the message names the plain letter to write (`write "e" in its place`), which is ASCII letters only. The characters are rejected rather than replaced, since outside a phrase `!`, `|`, `?`, `^`, and `~` are Lucene operators and `;` sits inside a term, so a space in their place would change the query's structure. Whitespace is the opposite case: every character `\s` matches reads as a separator in Lucene and is refused by openFDA unless it is a space, so it becomes one, inside a phrase and after a backslash too, which keeps every position the message names exact.

**Decision — an unquoted hyphenated term is sent as a quoted phrase.** Lucene reads a hyphen inside a term as part of it, so `D-0123-2024` is one term, but openFDA's analyzer splits it at the hyphens and ORs the parts: on `drug/enforcement`, `recall_number:D-0123-2024` answers the 18,148 records of `recall_number:(D OR 0123 OR 2024)` where the quoted form answers 1, and on `drug/ndc` the bare `0003-0894` answers 259, led by other labelers' products, where the quoted form answers 1. Keyword and date fields are not split and answer alike either way (`product_ndc:0003-0894`, `update_date:2026-11-20`). A notice would leave the unrelated records ranked first, so the term is quoted. Only a whole term of letters and digits joined by hyphens is quoted: one bounded by the start or end of the query, whitespace, or a group paren, or opening a `field:` value, with a leading `-` or `+` operator left outside the quotes. A term holding any other character (`D-0123*`, `1.5-mg`, `a\-b`) is left as written, and so is everything inside a quoted phrase, a `[…]` or `{…}` range, or a `/…/` regexp. The quoting runs after the whitespace and `+` normalization, inside the schema, so the handler, the staged path, the mirror gate, and the echoed query all hold the quoted string; a query holding a refused character is left as written so the position its rejection names counts the caller's own characters.

**Decision — `+` is a space only where it separates.** Reading every `+` as a space (openFDA's URL convention) regresses real data: `.exact` phrases and terms that contain a plus match nothing, and a leading `+field:` turns from AND into OR (435,387 → 12,065,512). The rewrite is limited to the separator positions, and a query written with Lucene's required operator keeps it. A phrase-internal `+` cannot be told apart from data, so it is never rewritten; an empty result whose phrase holds one gets a hint with the spaced form instead.

### Tool-composed: escape

`openfda_drug_profile` takes a `drug` name, not a query, and interpolates it, or the fan-out key derived from it, into every composed search — the label and NDC resolves, the adverse-event queries, and the recall, approval, and shortage searches. A drug name is not caller-written Lucene, so a name carrying a delimiter is not a caller error and must not surface as one.

**Decision — escape `\` and `"`, never strip them.** `\` is replaced first, since escaping `"` introduces backslashes of its own. Stripping only `"` (the original approach) left a term ending in `\` escaping the phrase's own closing quote, and the two failure shapes were both unusable: a two-clause resolve query answered **HTTP 200 with an unrelated result set** (`openfda.generic_name:"aspirin\" OR openfda.brand_name:"aspirin\"` returns 27,101 label records against 743 for the intended query — the escaped quote pulls ` OR openfda.brand_name:` inside the phrase and the remainder re-parses as a bare term), while a single-clause query left the phrase open and failed as `token_mgr_error`. Escaping keeps every composed query well-formed with the ` OR ` boundary intact.

**Escaping costs nothing in matches, which is why it beats stripping outright.** openFDA's analyzer discards the escaped delimiters as non-word characters, so the escaped term matches whatever the stripped term would have: `drug: 'Tylenol "Extra Strength"'` returns the same 29 label records either way, and `drug: 'aspirin\'` now returns the 743 of a plain `aspirin` search where stripping produced 27,101 unrelated ones. The caller gets results, not a `ValidationError` — and the term reaches openFDA as written rather than silently mutated.

**A term of only delimiters is still rejected.** `blank_drug_name` remains the declared reason, retested as "carries no character that could belong to a drug name" rather than "stripping emptied the string" — searching for the literal delimiters would return an unrelated record set as a profile.

### Out of scope, deliberately

Not guarded, each for a reason rather than by omission:

- **Field names, boolean structure, and non-sortable fields.** `openfda_describe_fields` covers discovery, and openFDA names the field in its own 400 — a full Lucene parser buys nothing. It lists field paths, not their sortable forms: a sort openFDA refuses answers `not_sortable`.
- **A `/.../` term carrying an unbalanced paren.** This is the one place the reject path is wider than openFDA: `reason_for_recall:/undeclared)/` is *accepted* upstream and answers 404 `No matches found!`, while the scanner reads the `)` as an unopened group and refuses it. Adding a fourth context would mean modelling Lucene's regexp grammar to know where the term ends, and the cost of not doing so is the one form: a regexp holding an unbalanced paren is refused here where openFDA would answer it. Every other regexp reaches openFDA as written, except one holding a refused character (`/a|b/`, `/colou?r/`), which openFDA refuses too; the slashes of a bare word are stripped by the analyzer, so `reason_for_recall:/undeclared/` and `reason_for_recall:undeclared` match the same `drug/enforcement` records.
- **Anything inside `OpenFdaService`.** The service forwards whatever string it is given; `tests/services/openfda/openfda-service-security.test.ts` asserts that pass-through. `openfda_drug_profile` declares no `malformed_search` reason — it has no caller-written query to reject.

**Pagination ceiling.** openFDA refuses a `skip` above 25000. For datasets larger than `skip + limit`, a walk by `cursor` from `skip` 0 reads past it until it reaches records openFDA cannot link on from, such as those lacking the sort field ([shared paging contract](#tools)); otherwise the agent narrows the search query (e.g., date ranges, additional filters).

**Decision — the ceiling is a handler check, not a schema `.max()`.** Every paginated tool advertises a `pagination_limit_reached` reason with recovery text. A schema maximum rejected the request as a generic input-validation failure first, so that contract carried no `structuredContent.error.data.reason` and no recovery hint — advertised but unreachable. The bound lives in `OPENFDA_MAX_SKIP` (`src/mcp-server/tools/schema-utils.ts`); handlers compare against it and `ctx.fail` the declared reason before spending an upstream request. `openfda_count_values` has no `skip` input, so it does not declare the reason at all.

**Rate limits:**
- Without key: 240 req/min, 1,000 req/day per IP
- With key: 240 req/min, 120,000 req/day per key
- Key is free, passed as `api_key` query parameter or Basic auth header

**`openfda` enrichment.** openFDA adds a harmonized `openfda` object (brand and generic names, manufacturer, RxCUI, pharm class, NDC, UPC) on top of the source data, but not everywhere: drug and device adverse events nest it under `patient.drug` and `device`, food, cosmetic, animal, and tobacco records have none, nor have Orange Book, Complete Response Letter, and NSDE records, and elsewhere it exists only where openFDA linked the record to a product (`device/classification` records carry one). An `openfda.*` miss is not proof of absence; each tool's empty-result notice names the endpoint's own product field.

**Data freshness.** Updated quarterly with potential 3+ month lag. Drug adverse events cover 2004-present. `meta.last_updated` in every response indicates the dataset date.

## Error Design

openFDA returns JSON error objects with `code`, `message`, and sometimes `details`. Map these to actionable tool errors:

| Error | API response | Recovery guidance |
|---|---|---|
| **Malformed search** | none — rejected locally before the request | `malformed_search`. A character openFDA refuses (checked first), an unterminated `"` phrase, an unbalanced `(`/`)` or `[`/`}` outside one, or a query ending on a backslash never reaches openFDA; the message names which of the seven faults it is — a refused character with its position (the character itself when printable ASCII, `U+XXXX` otherwise), or a delimiter fault with how to escape a literal delimiter. The trailing-backslash case would otherwise answer 200 with the endpoint's own scope filter dissolved. See [Query hygiene](#implementation-notes). |
| **Malformed sort shape** | none — rejected by the schema before the request | Schema `ValidationError` showing the expected form. A field path carrying a character no openFDA field path can hold, an empty comma-separated segment, or a direction other than `asc`/`desc`/`ascending`/`descending` (any letter case), which openFDA would silently drop. A well-formed path naming a non-sortable field still goes upstream. |
| **Malformed query** | `400` — `{"error": {"code": "BAD_REQUEST", ...}}` with Elasticsearch parse details | `query_error`. Surface the parse error. openFDA HTML-escapes the query its `error.message` echoes (`&quot;` for `"`); the server decodes that once, so the message reads as the query was sent (`decodeEntities`, `src/services/openfda/html-entities.ts`, applied in `upstreamMessage`, `openfda-service.ts`), and takes `error.details`, when openFDA sends one, as sent. Remaining causes after the local prechecks: invalid field names, wrong boolean syntax (a dangling `AND`/`OR`, lowercase operators read as terms). Guide agent to fix query syntax. |
| **Not sortable** | `400` `Sorting allowed by non-analyzed fields only: F`; `5xx` `No mapping found for [F] in order to sort on`; `5xx` `fielddata=true on [F]` on a request with no `count` | `not_sortable` (`ValidationError`), non-retryable, so it costs one request. It carries `data.endpoint` and `data.field` and is raised only when F is one of the request's sort keys; a refusal naming any other field stays `query_error`. The message names the key and the endpoint and drops openFDA's own advice text and index uuid. The recovery is the other form of the key (add or drop `.exact`), or another field: `.exact` cures analyzed text only where the field has a keyword subfield, dropping it cures an `.exact` the index lacks only where the bare field sorts, and a bare key with no mapping is a field the endpoint lacks, which no form cures. |
| **Not aggregatable** | `404` `"Nothing to count"`, or `5xx` `illegal_argument_exception` on a `count` query; also `404` `"No matches found!"` when the catalog records the expression as failing | `not_aggregatable`, non-retryable. openFDA answers a search that matched nothing before it reads the count expression, so a recorded-failing expression is rejected on that 404 too rather than returned as an empty tally that reads as countable. For a cataloged field the message is definitive: it names the recorded count expression when the caller used the other form, or says the field has no countable form and lists countable expressions on the endpoint — it never offers a form the catalog records as failing. For an expression outside the catalog it names the `.exact` correction in whichever direction applies — **drop** the suffix on a keyword field (the 404), **add** it on an analyzed text field (the 5xx) — and names `openfda_describe_fields` as the next step, since some fields fail both ways. The upstream `fielddata=true` advice is dropped — it is a server-side index setting no caller can reach. Only `openfda_count_values` declares the reason. |
| **Nothing to count, countable field** | `404` `"Nothing to count"` on a `count` query whose expression counts | Not an error — the search matched only records that carry no value for the field. Empty tally with a notice saying so. A cataloged countable expression resolves directly; one outside the catalog is confirmed with a single unscoped `limit=1` count, and a second `Nothing to count` there becomes `not_aggregatable`. The confirm gets one attempt: a transient failure propagates to the primary request's retry loop, which re-runs the scoped count and the confirm together, instead of retrying inside it and multiplying the budget. |
| **No results** | `404` — `{"error": {"code": "NOT_FOUND", "message": "No matches found!"}}` | Not an error -- the query was valid but matched nothing. Return empty results with a suggestion to broaden the search (remove filters, check spelling, and search the endpoint's own product field — on adverse events `patient.drug.medicinalproduct` or `patient.drug.openfda.brand_name` for drug, `device.brand_name` for device, `products.name_brand` for food, `products.product_name` for cosmetic, since no adverse-event record has a top-level `openfda` block; `products.brand_name` on Drugs@FDA; `spl_product_data_elements` on labels when an `openfda.*` field finds nothing). The no-match notice names the caller's `search` as a code span, so a wildcard or range reads back exactly from `content[]`. When a quoted phrase in it holds a `+`, the notice also gives the phrase's spaced form, because a phrase `+` is a literal plus (`reactionmeddrapt.exact:"INJECTION+SITE+PAIN"` matches 0 reports and `"INJECTION SITE PAIN"` matches 299,526 as of 2026-10-26). The staged path adds both the same way. `content[]` opens with the same metadata header a matched page carries (total, skip, limit, dataset date, and the canvas staging line when the call staged), then the tool's no-match line; an empty tally from `openfda_count_values` keeps its dataset date the same way. openFDA sends the same 404 for a page past the end of a matched set, so on a non-count query at `skip > 0`, or on a page read by `cursor`, the service makes one `skip=0&limit=0` request for the same `search` (no `sort`): a 200 carries the real total, and the page reports the offset as past the end; a second 404 confirms nothing matched. A page read by `cursor` reports the walk position, not an offset to lower: `No records at this cursor: its walk position (N) is past the last of the T matched records, so the cursor walk has ended`, with a re-run from `skip` 0 to read them again (`emptyResultMessage`, `src/mcp-server/tools/format-utils.ts`). The recovery is best-effort and gets a single attempt, with no retry backoff — if it fails the empty page returns at once, with `meta.totalUnverified: true` and both readings named. The staged arm never needs it: its `skip=0` probe already carries the total, and a window at or past it is not fetched. |
| **Skip ceiling** | `400` — `"Skip value must 25000 or less."` | Backstop only — handlers reject an over-ceiling `skip` locally with the typed `pagination_limit_reached` reason before the request goes out. The service matches only a message that opens with `Skip value must 25000`, since a refused search echoes its query in its message and a `25000` inside it is not this failure, and states only the ceiling; each tool's declared recovery names both routes past it: re-run the call from `skip` 0 and follow `next_cursor`, or narrow the `search` (date range, additional filters). |
| **Invalid cursor** | none — rejected locally before the request | `invalid_cursor`. A `cursor` that does not decode, was issued for a different endpoint, `search`, or `sort`, or comes with `skip` above 0, `stage: true`, or `canvas_id`; the message names which. Pass `next_cursor` exactly as returned, with the endpoint, `search`, and `sort` of the call that returned it and no `skip`, `stage`, or `canvas_id`, or start over from `skip` 0. |
| **Rate limit** | `429` — Too Many Requests | Without key: 240 req/min, 1K/day per IP. With key: 240 req/min, 120K/day. Retry after backoff, or after openFDA's `Retry-After` when it sends one: the `rate_limited` error carries it as `retryAfter`, and a wait longer than the retry budget fails fast instead of retrying. If hitting daily limit, suggest configuring an API key. |
| **Upstream 5xx, or a 200 that is not openFDA JSON** | `500`/`503` — `{"error": {"code": "SERVER_ERROR", ...}}`; or `200` with an HTML page, a body cut short, or JSON outside openFDA's envelope (`meta` and `results`) | Transient openFDA/Elasticsearch issue, or a proxy's page or a truncated transfer served as success. A 200 body is parsed against the envelope (`parseEnvelope`, `openfda-service.ts`); one that fails is `upstream_error` with `data.status: 200`, retried like a 5xx, and its message names the endpoint and an HTML page's `<title>` at most, never the body. Retry with exponential backoff (up to 3 retries after the first attempt). If persistent, surface as upstream outage -- not a client issue. Every attempt and backoff of one call settles within a 50 s deadline (`OPENFDA_CALL_DEADLINE_MS`); `openfda_drug_profile` passes one 50 s instant to all its requests. A backoff that would outlast it fails fast as `Timeout` (`retry_deadline_exceeded`), and a request the deadline leaves no time for is never sent. An HTML error page from the proxy in front of openFDA contributes only its `<title>` to the message, never its markup. The message is built as a `query_error`'s is: `error.details` as sent when openFDA supplies it, otherwise `error.message` decoded once from its HTML escaping. |
| **Invalid endpoint** | `404` — no JSON body (plain 404) | The endpoint path doesn't exist. Check for typos in the endpoint enum. |

**Implementation notes:**
- All tools should normalize these into structured error responses with `code`, `message`, and `recovery` fields.
- The `NOT_FOUND` case (valid query, zero results) should not be thrown as an error -- return it as an empty result set with `meta.total: 0`.
- Rate limit handling should be centralized in the service layer with automatic retry + backoff.

## Config

| Env var | Required | Description |
|---|---|---|
| `OPENFDA_API_KEY` | No | Free API key from [open.fda.gov](https://open.fda.gov/apis/authentication/). Increases daily limit from 1K to 120K requests. Passed as `api_key` query parameter. |
| `OPENFDA_BASE_URL` | No | Base URL override. Default: `https://api.fda.gov`. Useful for testing against a proxy or mock server. |
| `OPENFDA_CLAMP_LIMITS` | No | Default `true`: a `limit` above its endpoint's cap returns the cap's worth with a notice (requested value, cap, next `skip`), one log line, and one `openfda.limit.clamped` increment. `false` advertises the cap as the schema `maximum` and rejects a larger value before any request (`-32602`; `limit_above_cap` between an endpoint's cap and the tool's largest cap on the multi-endpoint tools). Parsed strictly as a boolean word. |
| `CANVAS_PROVIDER_TYPE` | No | [DataCanvas staging](#datacanvas-staging-analytical-sql) — analytical SQL over result sets staged with `stage: true` and queried via `openfda_dataframe_query`. Default `duckdb`; `none` disables it. Requires the `@duckdb/node-api` dependency; unsupported on Cloudflare Workers. |
| `OPENFDA_DATAFRAME_DROP_ENABLED` | No | Set to `true` to make `openfda_dataframe_drop` callable. Default `false` (listed as disabled). Meaningful only with `CANVAS_PROVIDER_TYPE=duckdb`. |
| `OPENFDA_MIRROR_ENABLED` | No | Set to `true` to enable the [local bulk mirror](#local-bulk-mirror). Default `false`. Requires an out-of-band `bun run mirror:init` before it serves anything; on Node, the optional `better-sqlite3` peer dependency. Unsupported on Cloudflare Workers. |
| `OPENFDA_MIRROR_PATH` | No | Directory holding one SQLite file per mirrored dataset. Default `./data/openfda-mirror`. |
| `OPENFDA_MIRROR_REFRESH_CRON` | No | Cron expression for the in-process refresh. HTTP transport only; unset means no scheduled refresh. Requires the optional `node-cron` peer dependency — set without it, the server fails to start. |
| `OPENFDA_MIRROR_FALLBACK_LIVE` | No | Fall back to the live API when the mirror is cold, missing the record, or failing. Default `true`. |
| `OPENFDA_MIRROR_REFRESH_TIMEOUT_MS` | No | Wall-clock budget for one refresh before it is aborted. Default `21600000` (6h). |
| `OPENFDA_MIRROR_BASE_URL` | No | Host serving the bulk download manifest (`download.json`). Default `https://api.fda.gov`. |
